통합 콘텐츠 배포 시스템
개발 플랜

Blog Posting Kit v1.07 · Instagram Auto Posting Kit v1.11 · Threads Auto Posting Kit v1.02를 기존 사이트에 통합하기 위한 단계별 제품·보안·운영 계획

총괄 결정과 권리 관문

세 킷은 독립된 Next.js/Supabase/Vercel 서비스이며 회원별 BYOK, 테이블, 예약 실행 구조가 각각 다릅니다. 기존 사이트의 src/lib/distribution 계약(승인, 멱등키, 재시도, unknown 대사)을 중심으로 신규 통합 기능을 설계하고, 킷 전체 앱이나 SQL은 가져오지 않습니다.

각 NOTICE는 BUYLIFE 권리와 사전 서면 허락 없는 추출·복제·수정·배포 제한을 명시합니다. 수강생 배포가 현재 사이트로의 통합·수정까지 허용하는지 확인되지 않았습니다. 서면 허가 범위 확인 전에는 키트 코드·프롬프트·스키마 재사용을 보류합니다. 불명확하면 공식 플랫폼 자료와 독립 요구사항으로 clean-room 구현합니다.

추가 검토 결과 반영

  • UX 명세 검토 완료: 첫 콘솔은 기존 관리자 진입점에 두고, 승인/버전, API 연결, 게시 결과를 별도 상태축으로 표시합니다. 원본 변경 시 미실행 예약을 stale 차단합니다.
  • 단일 운영자 Threads Tester 및 Instagram Standard Access로 제한된 MVP 검토가 가능하다는 공식 문서 확인 결과를 반영했습니다. 다계정 외부 공개는 App Review 등 별도 게이트입니다.
  • 네이버는 수동 내보내기와 사람 게시만 유지합니다. 게시 URL 자동 수집이나 브라우저 자동 입력은 포함하지 않습니다.
  • Vercel Hobby Cron은 하루 1회/±59분 정확도로 예약 게시에 적합하지 않습니다. Pro Cron 또는 이용 가능성을 확인한 Supabase pg_cron 중 선택이 필요합니다. 두 API 모두 idempotency key가 확인되지 않아 컨테이너 ID 선저장·대사가 필요합니다.
  • Threads 계정 공개 여부/90일 권한 갱신, Instagram 권한명과 게시 한도(공식 문서 값 불일치), 공개 JPEG 미디어, `published_with_issues`를 데이터 계약·테스터 검증 게이트로 올렸습니다.

출처와 불확실성 상세: API readiness 결과 · UX 명세

Master 데이터 결정

  • 배포 권한은 승인 상태가 approved인 admin만 허용합니다. 기존 전역 admin 판정은 유지하고 배포 전용 판정을 추가합니다.
  • unknown → confirmed_absent는 자동 재게시 권한이 아닙니다. 운영자 재실행 승인과 전체 조건 재검사를 요구합니다. 기존 retryable만으로 자동/수동 재시도를 구분하지 못하므로 live 발행 전 계약을 보강합니다.
  • 다음 단계로 AUTOPOST-M1-CONTENT-001을 배정했습니다. 첫 migration은 콘텐츠 버전·채널 초안 리비전·승인·전용 RLS/grants에 한정하며 DB 적용·실행 검증은 수행하지 않습니다.

DEC-AUTOPOST-DATA-001 결정 기록 · 데이터 계약 제안 원문

M1 migration Master 검토

동일 트랜잭션 안에서만 리비전 미디어를 추가하도록 하는 조건을 정적 검토 중 보완했습니다. `created_at=now()` 비교만으로는 충분하지 않아 내부 전용 `xid8` 트랜잭션 ID로 비교하도록 수정했고, 이 열은 authenticated 읽기 권한에서 제외했습니다. PostgreSQL 문서는 pg_current_xact_id()가 `xid8`을 반환하고 최상위 트랜잭션 ID를 제공한다고 설명합니다.

M1 migration 파일은 정적 검토를 통과했습니다. DB/PGlite 검증은 미실행 상태이므로 Supabase 적용 전 별도 검증이 남아 있습니다. 다음 작업은 AUTOPOST-M2-JOBS-001입니다.

2. 제품 흐름과 상태

수집/작성 → 편집 → 채널별 초안 → 권리·사실·링크 검토 → 승인 → 예약 또는 수동 내보내기 → 게시/확인 → 증거 등록 → 성과 측정

공통 콘텐츠

원본, 버전, 출처, 작성자, 미디어 및 권리 근거를 보관합니다. 승인 후 원본이 수정되면 새 버전을 만들고 과거 초안/예약을 stale로 표시합니다.

API 게시

scheduled → dispatching → published | failed | unknown. 외부 ID나 검증된 게시 URL 증거로만 완료 처리합니다.

수동 게시

approved → manual_ready → awaiting_evidence → published | abandoned. 운영자가 게시 URL 또는 외부 ID를 등록합니다.

불확실한 결과

unknown은 자동 재시도하지 않습니다. 외부 대사 또는 운영자 증거 확인을 먼저 요구합니다.

3. 목표 구조와 데이터 경계

  • 기존 web/의 인증·승인·콘텐츠와 공통 배포 계약을 사용합니다.
  • 서버 전용 어댑터에 OAuth 토큰과 플랫폼 호출을 격리하고 사용자 권한·승인·콘텐츠 버전·미디어 권리를 매 실행 때 재검증합니다.
  • 제안 테이블: distribution_channel_connections, distribution_channel_drafts, distribution_jobs, append-only distribution_job_events, distribution_media_assets.
  • 토큰은 브라우저에서 읽을 수 없는 암호화 저장소/비공개 스키마에 둡니다. RLS, SQL grants, column 권한, Storage 정책을 함께 검토하고 service/secret key는 서버에만 둡니다.
  • Job은 원자적으로 claim하고 lease/heartbeat/attempt를 남깁니다. DB unique idempotency key로 중복 생성·선점을 막고, timeout/프로세스 종료 시 먼저 원격 결과를 대사합니다.
  • 미디어는 출처·권리·동의·MIME·크기·해시를 기록합니다. 공개 URL은 게시에 필요한 동안만 허용하고 일괄 30일 삭제를 기본값으로 두지 않습니다.

예약 기능은 Hobby Cron으로 제공하지 않습니다. 현재 선택지는 Vercel Pro Cron 또는 Supabase pg_cron이며, 실제 계정 플랜 확인 후 결정합니다. Queue는 단일 운영자 소량 처리의 MVP 필수 요소가 아닙니다.

5. 보안·운영 완료 기준

  • 승인되지 않은 문안, stale 버전, 권리 없는 미디어, 잘못된 URL은 live job으로 전환되지 않습니다.
  • 같은 작업은 동시에 한 worker만 claim하며 같은 idempotency key는 한 번만 저장됩니다.
  • timeout/작업 중단으로 게시 여부가 불명확하면 unknown으로 남고 자동 재전송되지 않습니다.
  • 토큰·시크릿은 브라우저 응답/RLS를 통해 노출되지 않습니다. OAuth state는 일회용 nonce이며 로그인 세션에 결합됩니다.
  • 수동·자동 게시 모두 증거를 갖추기 전에는 published가 되지 않습니다. 부분 성공과 재인증 필요 상태를 숨기지 않습니다.
  • 예약 지연, 취소, 철회, 토큰 만료, 미디어 정리, 감사 이벤트, 운영 중지/재개 흐름이 정의돼야 합니다.
  • 기존 migration/auth/content 계약과 분리된 변경 경계를 유지합니다. 배포 전 백업·복구, 채널 kill switch 및 이미 게시된 외부 콘텐츠 처리 절차를 준비합니다.
