## 5. Backend 상세 작업

DB: 적용 이력과 실제 객체를 먼저 대조한다. 초기 SQL Editor 수동 적용 기록이 있어 파일 존재만으로 migration 완료를 판단하지 않는다. 기존 적용 SQL은 변경하지 않고 forward migration을 사용한다. NOT VALID FK는 기존 고아 참조 목록·정리 방안·검증 결과를 남기며 자동 삭제하지 않는다.

조회/관리: 상태별 정확한 집계와 최신 목록을 분리한다. 사용자 세션+RLS와 명시 열을 유지하고 토큰·암호문·원문 오류를 반환하지 않는다. 필터/페이지/정렬은 서버에서 제한한다. 연결 조회는 유효/만료/철회/재인증·요청권한/실부여권한·게시준비를 구별한다.

쓰기: actor는 검증된 세션에서만 도출, D1은 page/액션/RPC에서 재검사한다. 렌더된 expected version/hash를 최신값으로 덮지 않는다. uncertain은 재조회로 확인하고 자동 재요청하지 않는다. 확인된 부재 이후 재실행은 별도 사유·대사ID·최신 승인·권한·gate 검사를 거친 운영자 승인 기능으로 만든다.

실행/복구: worker가 상태를 임의 갱신하지 않고 RPC를 사용한다. 작업 버전·리스·attempt·컨테이너ID·증거를 고정한다. publish 후 불명은 대사만, permalink 실패는 게시실패로 바꾸지 않는다. 회수 호출자는 recovery_failed를 정상 JobStatus로 취급하지 않으며 한 작업의 오류가 배치 전체를 막지 않도록 경보한다.

미디어: 실제 Storage 어댑터·bucket 정책·서명URL 유효시간·고아 파일 정리·참조 보호를 운영 검증한다. 권리승인/ready/채널/만료/변형sha를 재검사한다. 이미지 컨테이너를 만들 때 사용한 자산/변형이 중간에 바뀌지 않게 고정한다.

## 6. Front·Design 상세 작업

A안 공통 원문 중심 탐색을 유지한다. /me→관리→콘솔, 보관함→원문→채널초안→검토→실행준비→작업상세가 연결돼야 한다. 실제 서비스 준비 전·조회오류·성공0건·충돌·불확실결과·부분실패를 서로 다른 상태로 제공한다.

Front는 Backend가 게시한 DTO/오류/액션계약을 소비한다. 전달계약 없이 임의 상태를 추가하지 않는다. Design은 실제 렌더·CSS우선순위·960/700/320px·키보드·초점·label·표·확대/대비를 검토하고 파일/심벌 단위 개선을 제출한다. 실제 승인 admin 테스트는 명시적인 테스트 계정으로 하며 운영 인증 우회 코드를 만들지 않는다.

유입 목적은 콘텐츠→사이트 목적 페이지→참여 안내의 흐름으로 측정한다. 승인된 대상 URL·UTM과 캠페인 참조를 유지하고 모의실행/확장입력/실제게시/방문을 다른 지표로 센다. 게시수·조회수·유입수는 실제 근거 없이 표시하지 않는다. 거래/정산/배송·회원상품 기능은 콘텐츠 배포 우선 작업의 뒤에 둔다.

## 8. 운영 연결 준비와 검증

설정 항목은 변수명·대상환경·설정유무만 기록한다. 기존 공개Supabase 설정 외 SUPABASE_SECRET_KEY, DISTRIBUTION_TOKEN_KEY, THREADS_APP_ID/SECRET, INSTAGRAM_APP_ID/SECRET, 고정 SITE_URL, private media bucket 및 공급자 callback 등록이 필요하다. 값을 채팅·기획·소스에 담지 않는다.

로컬 순수시험→PGlite/RPC왕복→실제 테스트 Supabase/PostgREST/JWT·두연결 경합→브라우저실세션→공급자 테스트 계정→배포후 연기시험 순으로 증거를 쌓는다. skip은 통과에 합산하지 않는다. M4 fixture는 실제 ready 자산을 생성해 보완하며 제약완화로 통과시키지 않는다.

코드·mock만 통과한 기능을 운영완료로 승격하지 않는다. release별 포함/제외 파일·커밋SHA·Vercel ID·DB 적용버전·실측 범위를 남긴다. 새 기능이 미배포라면 현재 운영판과의 차이를 표시한다.

## 9. 실행·보고 운영

각 세션의 사용자 직접지시는 즉시 수행하되 작업ID·수정예정파일·지시출처·완료조건을 Master에 공유한다. 겹치면 해당 구간만 순서를 조정하고 독립범위는 진행한다. 결과는 각자 고유 results, 공통 TEAM/점유/계획/히스토리는 Master가 갱신한다.

완료보고에는 변경파일·명령/exit·시험환경·pass/skip·실측/미실측·남은오류·인계와 최종hash를 적는다. Master는 보고를 검토해 수정·인계·다음배정을 지시한다. 현재 완료/차단/다음 작업을 한 시점의 기준표로 제공하며 오래된 사건은 히스토리로 보존한다.

바로 다음 순서: Backend가 M4 회귀·저장 어댑터 계약을 인수 → Front가 미디어/관리 UI를 계약 기준으로 연결 → Master가 운영 DB/설정 반영 묶음을 검토 → Blog 실제 흐름부터 검증. Instagram OAuth는 Backend의 다음 독립작업으로 준비하고 live 활성은 채널별 관문 뒤로 둔다.
