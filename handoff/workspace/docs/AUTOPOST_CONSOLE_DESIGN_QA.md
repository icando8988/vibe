## 1. 판정과 검토 경계

현재 구현은 보호된 관리자 콘솔의 **준비 전 골격**으로는 설계의 주요 경계를 지킨다. admin 안의 단일 진입 카드, 공통 콘텐츠→채널별 편집, Blog 제목/본문·Threads 텍스트/링크·Instagram 캡션/이미지 설명의 차이, disabled 행위와 사유, 데이터 미연결, live gate 닫힘, unknown 재게시 CTA 부재를 코드에서 확인했다. 다만 CSS 우선순위·좁은 화면 탐색·운영 안내에 아래 개선이 필요하며 원문 저장부터 Blog 수동 준비까지 실제 사용 흐름이 완성된 것은 아니다.

기존 CC-ENG 검증 보고는 typecheck/lint/build와 역할 판정 8케이스 통과를 보고한다. 이번 QA는 그 명령을 재실행하지 않았다. 해당 통과가 렌더링·접근성·데이터 연결·플랫폼 게시 성공을 증명하지 않는다. P0/P1 실행 결함을 이번 정적 UI 검토에서 입증하지 않았으며, 현재 개선 8건은 P2다. 별도의 이식 명세 갭 3건은 최신 원본 기반 이식 방향을 반영할 **범위 정합화 요구**이고, 현재 비활성 골격에 동작 결함이 있다고 판정한 것이 아니다.

검토 입력:

- `docs/AUTOPOST_CONSOLE_UI_PLAN.md`, `docs/AUTOPOST_CONSOLE_WIREFRAME.html`, `.ai/results/AUTOPOST-CONSOLE-VERIFY-001-CC-ENG.md`.
- `web/src/app/admin/distribution/**`의 page 14개, layout/loading/error와 `web/src/components/distribution-console/{access,guard,console-shell,readiness,states}` 전체.

- 후속 조정자 메시지 `msg_13c43bdac617`: 최신 지시는 제공된 **원본 소스 기반 이식 후 수정**이며, Claude가 모듈 매핑 중이다. 이에 따라 기존 Blog/Threads/Instagram 분석 보고서의 기능 목록을 추가 대조했다(§5). 과거 보고서의 clean-room 권고를 현재 이식 방향을 막는 새 승인 요구로 사용하지 않는다.

브라우저·외부 네트워크·실DB·키/env·commit 작업은 하지 않았다. 프로그램 원본 소스·프롬프트·화면·자산은 이번 QA에서 열거나 복사하지 않았고 기능 목록 보고서만 읽었다. 아래 줄 번호는 이번 열람 시점 기준이다. 실측 항목은 결함 확정과 구분했다.

## 2. 현재 확인된 개선 항목

### DQ-01 · 콘솔 제목/간격 CSS가 공통 스타일에 덮인다 — P2

- **파일/위치:** `web/src/app/globals.css:39`의 `.dc-content h1`, `:97`의 `.dc-block > h2`, `:115`의 `.dc-card h3`, `:184`의 `.dc-reason`; `web/src/styles/design.css:24~27`; import 순서 `web/src/app/layout.tsx:4~5`.
- **사실:** h1 두 선택자는 특정성 (0,1,1)이 같고 design.css가 뒤에 온다. 따라서 콘솔 `clamp(1.8rem,3.2vw,2.4rem)` 대신 공통 `clamp(2rem,4.6vw,3.8rem)`이 이긴다. h2 크기도 같은 이유로 공통 값이 이긴다. `.dc-card h3`의 margin-top:0은 공통 h3 margin으로, `.dc-reason`의 margin:0은 더 높은 특정성의 `.ds-main p`로 덮인다. fieldset 규칙이 통째로 덮인다는 근거는 발견하지 않았다.
- **사용자 영향:** 의도한 콘솔 밀도·설명 간격이 적용되지 않는다. 큰 제목과 반복 공백이 편집/상태 정보를 아래로 민다. 실제 접힘 위치·시각 손상 정도는 실측 필요다.
- **권고:** 콘솔 범위 안의 선택자 특정성을 의도적으로 정리하거나 공통 토큰 다음에 콘솔 스타일이 오도록 구성한다. 전역 글꼴/제목 전체를 바꾸거나 !important를 남발하지 않는다.
- **수락 조건:** h1/h2·카드 제목·사유 문단 각각 computed style이 의도한 콘솔 값이며 공개 페이지는 유지된다. 961/960/701/700/320px 및 200%에서 제목·본문·행위가 잘리지 않는다.

### DQ-02 · 검색/필터 필드에 기존 폼 타이포그래피가 적용되지 않는다 — P2

- **파일/위치:** `web/src/app/globals.css:168~174`; `web/src/app/admin/distribution/contents/page.tsx:26~50`, `jobs/page.tsx:19~52`; 비교 `web/src/styles/design.css:96`.
- **사실:** `.dc-filters`의 input/select는 min-height/max-width만 받는다. font:inherit·텍스트/배경·패딩·테두리 규칙은 `.ds-editor-fields`에 한정되어 이 검색 폼에는 매칭되지 않는다. 일반 버튼과 달리 입력 텍스트는 body 글꼴을 확실히 계승하도록 선언하지 않았다.
- **사용자 영향:** 같은 콘솔 안에서 편집 필드와 필터 필드가 다른 브라우저 기본 글꼴/표현으로 보일 수 있다. 48px 높이만으로 글자 가독성은 확보되지 않는다. 실제 UA 기본값/대비는 실측 대상이다.
- **권고:** 콘솔 검색 필드에도 기존 필드의 font·padding·ink/paper·border·min-width 규칙을 명시적으로 공유한다.
- **수락 조건:** 필터/편집 필드의 글꼴·크기·높이와 disabled 사유가 일관되고 긴 옵션/확대/forced-colors에서 잘리지 않는다. 색만으로 비활성 여부를 설명하지 않는다.

### DQ-03 · 700px 이하 채널 이동 링크가 세로 전환되지 않는다 — P2

- **파일/위치:** `web/src/app/globals.css:88~93`, `:206~213`; `contents/[contentId]/channels/[channel]/page.tsx:40~50`.
- **사실:** `.dc-channel-links ul`은 모든 폭에서 display:flex/flex-wrap이며 700px 규칙에 해당 항목 전환이 없다. 설계 §2의 좁은 화면 세로 링크와 차이가 있다. 가로 넘침을 실제로 재현한 것은 아니다.
- **사용자 영향:** 채널명이 행마다 불균일하게 감기며 모바일 탐색 순서/현재 채널 구분이 약해질 수 있다. 백엔드 연결 후 검토/결과 배지를 더하면 밀도 문제가 커진다.
- **권고:** 700px 이하 링크 목록을 한 열로 전환하고 채널명과 현재 상태를 읽는 순서를 유지한다. 모바일 콘솔 전체 메뉴의 960px 전환은 별도로 유지한다.
- **수락 조건:** 700/699/320px에서 세 채널이 한 열이고 각 타깃 최소 44px이며 현재 채널이 텍스트/aria-current로 식별된다. 701px 이상의 배열은 콘텐츠에 맞게 유지된다.

### DQ-04 · 회원 영역에서 관리자 진입을 발견할 경로가 없다 — P2

- **파일/위치:** `web/src/app/me/page.tsx:58~65`; `web/src/components/site-header.tsx:19~22`; `web/src/app/admin/page.tsx:38~48`. 참고 `login/page.tsx:62`의 기본 returnTo `/me`.
- **사실:** `/admin` 안의 배포 진입 카드는 D1 확인 뒤 제공되지만 공개 메뉴에는 관리 링크가 없고 승인 회원의 `/me`에는 로그아웃만 있다. 확인한 일반 로그인 흐름의 기본 복귀는 `/me`다. 따라서 해당 경로에서 승인 admin이 `/admin`을 탐색으로 찾을 링크가 없다. 다른 외부 즐겨찾기 존재는 판단하지 않았다.
- **사용자 영향:** 콘솔을 사용하려면 관리자 주소를 별도로 알아야 한다. 관리 안의 발견성은 충족하지만 사이트에서 관리로 들어오는 경로는 닫혀 있다.
- **권고:** 후속 공용 회원 영역 작업에서 서버가 권한 확인 후 ‘관리’ 진입을 제공한다. 공개 nav에 운영 메뉴/건수를 일괄 노출하지 않는다. `/admin` 배포 카드의 D1 판정은 유지한다.
- **수락 조건:** 승인 admin은 기본 회원 영역→관리→콘솔로 이동할 수 있다. 일반 회원/비로그인/비승인 admin에게 배포 진입 및 운영 데이터가 노출되지 않는다. 관련 공용 파일 변경은 Master가 Claude에 별도 배정한다.

### DQ-05 · 대사 화면에 결과 불명 경고와 재전송 금지의 핵심 설명이 약하다 — P2

- **파일/위치:** `jobs/[jobId]/reconcile/page.tsx:35~49`, `:68~72`; 비교 설계 §4D와 HTML `#reconcile`.
- **사실:** 현재 화면은 일반 회색 문장으로 대사를 정의하고, ‘부재 확인’ disabled 사유에서만 재게시 허가 아님을 설명한다. 설계의 ‘외부 게시가 완료됐을 수 있습니다. 확인 전에는 다시 게시하지 않습니다’ 경고는 없다. 재게시·재시도·복제 CTA 자체는 없으며 이 점은 충족한다.
- **사용자 영향:** 서버 복구 여부와 외부 게시 부재가 다르다는 판단 이유를 놓칠 수 있다. 현재는 모두 비활성이므로 재전송 동작이 발생한다고 주장하지 않는다.
- **권고:** 작업 미연결 상태에는 ‘결과 불명일 때의 안내’임을 명시한 주의문을, 실제 unknown을 조회한 뒤에는 상태에 맞는 경고를 상단에 제공한다. 단순 조회 실패≠부재, 연결 복구≠대사 해소를 설명한다.
- **수락 조건:** 실제 사건을 꾸미지 않는 빈 상태 안내가 있고 unknown에서 경고를 항상 읽을 수 있다. 대사 전 화면·복귀·일괄 메뉴 어디에도 재게시 CTA가 없다. 부재 확인 뒤 재실행은 별도 운영자 승인과 서버 재검사로만 가능하다.

### DQ-06 · 개발 의존성이 기본 사용자 정보 계층에 섞여 있다 — P2

- **파일/위치:** `web/src/components/distribution-console/states.tsx:189~200`의 Dependencies; 예: `contents/new/page.tsx:35~41`, `channels/[channel]/page.tsx:101~105`, `jobs/[jobId]/manual/page.tsx:81~86`.
- **사실:** 사용자 화면의 h2 ‘연결에 필요한 것’ 아래 RPC·D1·리비전 해시·M1/M2/M4 등 개발 계약을 상시 본문으로 표시한다. 비활성 사유에도 내부 함수/단계 이름이 반복된다.
- **사용자 영향:** 사용자가 할 수 있는 내용 검토와 개발자가 해결할 시스템 연결이 같은 과제로 보인다. 새 원문 작성→채널 검토의 핵심 흐름을 찾기 어렵게 한다.
- **권고:** 기본 화면은 ‘원문 저장 연결을 준비 중입니다’처럼 현재 가능 행위/다음 상태를 설명한다. 기술 의존성은 QA/구현 명세에 보존하고 필요하면 운영 진단 details로 낮춘다. 사용자가 직접 DB/RPC를 설정해야 한다고 안내하지 않는다.
- **수락 조건:** 기본 본문만 읽어 현재 가능/불가능과 복귀 위치를 알 수 있다. 기술 진단을 접어도 차단 이유·현재 모드·권리/승인 정보가 사라지지 않는다.

### DQ-07 · 상태 사전에 검토·연결·경고 보조축이 빠졌다 — P2

- **파일/위치:** `web/src/components/distribution-console/states.tsx:148~187`; 사용 `jobs/page.tsx:60~63`, `contents/[contentId]/prepare/page.tsx:80~83`; 비교 설계 §6·HTML W9 상태 사전.
- **사실:** StatusDictionary는 JobStatus 값만 순회한다. `published_with_issues`(published+issues), stale/approval, reauth/readiness 등 독립축 설명은 사전에 없다. 일부 페이지 문장으로 개념은 설명하지만 구분된 상태 안내는 구현되지 않았다.
- **사용자 영향:** ‘게시 확인+구성 경고’를 실패나 재게시 대상으로 해석하거나 재인증 완료를 기존 작업 성공으로 오인할 수 있다. 현재 실제 데이터가 없으므로 실제 결과가 잘못 표시됐다는 판정은 아니다.
- **권고:** JobStatus 사전 아래 ‘검토·연결·보류·구성 경고’ 보조 설명을 추가한다. JobStatus union에 없는 값을 억지로 넣지 않고 후속 DTO의 실제 축으로 연결한다.
- **수락 조건:** published+issues는 증거와 구성 경고를 함께 보존하고 재게시를 유도하지 않는다. stale·재승인, 재인증·기능 미검증을 상위 결과와 별도 읽을 수 있다. 설명에는 ‘상태 사전·실제 작업 아님’ 표시를 유지한다.

### DQ-08 · 실행 상세의 주요 다음 행동이 최소 터치 타깃 규칙을 공유하지 않는다 — P2

- **파일/위치:** `jobs/[jobId]/page.tsx:40~46`; 비교 `web/src/styles/design.css:63` 및 `globals.css:56~65`.
- **사실:** ‘Blog 수동 게시·증거’, ‘대사·오류 검토’ 링크는 일반 inline Link이며 ds-text-link나 콘솔 44px 타깃 규칙이 없다. 다른 주요 복귀/탐색 링크는 해당 클래스를 사용한다.
- **사용자 영향:** 모바일에서 핵심 복구·증거 동선의 터치 영역이 일반 본문 크기에 머물 수 있다. 실제 hit area/인접 여백은 브라우저 확인 필요다.
- **권고:** 핵심 다음 행동 링크에 최소 44px의 기존 텍스트 링크/목록 액션 패턴을 적용한다. ‘수동 방식 작업일 때’ 같은 조건은 향후 실제 mode/status 기반 노출로 바꾼다.
- **수락 조건:** 두 주요 타깃의 실제 영역이 최소 44px이고 겹치지 않으며 키보드 focus가 잘리지 않는다. 실제 unknown 작업에서는 수동 게시 준비로 우회하지 않고 대사 동선만 제공한다.

## 4. 원문 작성 → 초안 → 승인 → Blog 수동 준비 연결 전 보완

여기서는 현재 모두 비활성인 기능을 즉시 활성화하라고 요구하지 않는다. Claude의 백엔드 연결 배정에서 화면과 서버 조건을 함께 완성할 수락 기준이다. 입력 활성화만으로 완료 처리하면 안 된다.

| 단계/현재 위치 | 디자인 보완과 상태 흐름 | 연결 후 수락 조건 |

## 5. 최신 원본 기반 이식 방향에 대한 기능 대조

추가 입력은 기존 분석 보고서의 **기능 목록**이다. Blog 보고서 §3(약 70~113행), Threads §3~4(수집/생성/편집/즉시/예약), Instagram §2.3~4.2(약 61~92행)를 중심으로 읽었다. 보고서의 ‘확인’은 당시 분석자의 정적 관찰이며 이번 QA가 원본/API를 재검증했다는 뜻이 아니다. 원본 기능 목록 전체를 승인된 MVP로 자동 승격하지 않는다. ‘원본 기반 이식’은 구현 방식의 최신 방향이며 현재 manual·단일 이미지·준비 전 gate를 자동 해제하는 지시는 아니다.

### IGAP-01 · 공통 글감 수집→선택→생성→검토 흐름이 IA에 없다 — P2 / 이식 범위 확정 시 필수 명세

- **근거/위치:** Blog 분석 §3.1~3.2는 URL/RSS·뉴스/트렌드·쇼츠 후보→본문/이미지 생성→편집을 보고한다. Threads 분석 §3.1, Instagram 분석 §3도 URL/RSS/트렌드 후보·문안/이미지 생성 경로를 보고한다. 현행 `contents/page.tsx:20~56`, `contents/new/page.tsx:20~35`와 설계 W2/W3에는 수동 원문 작성만 있다.
- **사용자 영향:** 현재 콘솔을 ‘3개 프로그램의 핵심 기능 이식 완료’라고 부르면 원본의 글감→생성 입구가 빠진다. 수동 원문에서만 시작할 수 있어 원본 이용자의 작업이 이어지지 않는다.
- **권고:** Claude 매핑 결과와 함께 ‘콘텐츠’ 아래 **글감/수집 이력 → 후보 검토 → 선택한 후보에서 원문 준비 → 채널 초안**의 후속 IA를 명세한다. 생성은 검토 필요 초안을 만들고 즉시 승인/게시하지 않는다. 뉴스/실적 사실을 자동으로 참으로 취급하지 않는다. 공급자/모델·예산은 정책 확정 후 표시하며 키 입력 예시는 두지 않는다.
- **수락 조건:** 후보 출처/수집 시각/선택 상태·중복·수집 오류/생성 중/부분 실패/기존 결과 보존/사용자 취소의 화면 계약이 있다. 생성 응답 유실 시 반복 생성/과금 가능성을 분리해 안내한다. 지원 범위를 ‘이식 예정/이번 제외/미검증’으로 기능별 기록하고 모델·가격·성공 예시는 창작하지 않는다.

### IGAP-02 · Blog 원본의 서식·이미지·태그·내보내기와 확장 인계 경계가 현 콘솔보다 넓다 — P2 / 원본 이식 매핑 필요

- **근거/위치:** Blog 분석 §3.2~3.5는 HTML 편집/이미지, 카테고리·태그, rich/plain 복사, 네이버 확장 입력 준비→사람 최종 발행, 이후 서버로 게시 URL을 자동 회수하지 않는 구조를 보고한다. 현행 `channels/[channel]/page.tsx:62~68`은 제목/본문 textarea, `manual/page.tsx:51~54`는 승인본 미연결 안내만 있다.
- **사용자 영향:** 원본의 편집/내보내기 방식이 단순 텍스트로 축소되며 이미지·링크·서식 보존과 대상 분류의 의미가 사라진다. 향후 확장 인계를 `published`와 혼동할 위험이 있다.
- **권고:** 수동 게시 MVP는 유지하면서 이식 가능한 서식 블록·이미지/링크·태그/카테고리·복사 형식을 매핑한다. 원본 확장 경로는 Claude의 모듈/운영 범위 결정과 별도 연결 준비도에 따르며 현재 UI에 작동한다고 추가하지 않는다. 인계 접수/입력 준비/사람 최종 발행/증거 대기를 구분하는 상태 설계가 필요하다.
- **수락 조건:** 원본 기능 중 가져오는/수정하는/제외하는 범위가 문서화된다. 서식 미리보기는 안전한 표현, 이미지 권리와 영속 수명 안내를 포함한다. 입력 준비 완료≠게시 완료, 확장 계정 불일치·기존 편집 내용·인계 실패는 완료로 꾸미지 않는다. Blog live API 자동 게시/예약 기능을 새로 있다고 표현하지 않는다.

### IGAP-03 · Threads 이미지·Instagram 슬라이드/생성·예약 운영이 의도된 MVP 축소인지 명시가 필요하다 — P2 / 후속 단계 분리

- **근거/위치:** Threads 분석 §3.2~3.3은 직접 이미지/사진 검색·생성·다중 이미지와 draft/즉시/예약 선택을 보고한다(영상은 파일명만 저장해 실제 UI 게시 미연결이라고 명시). Instagram 분석 §2.3/§3/§4는 피드 1장/캐러셀, 직접 첨부·캡션/이미지 생성·슬라이드 교체·예약 운영을 보고하며 독립판 카드뉴스 스튜디오는 사용 가능 범위가 제한된다고 밝힌다. 현행 채널 편집 `:69~81`, `media/page.tsx:15~24`, `jobs/page.tsx:19~58`은 Threads 텍스트·Instagram 단일 이미지 설명·빈 큐만 있다.
- **사용자 영향:** 현재 단일 이미지/텍스트 MVP를 원본 전체 이식으로 오인할 수 있다. 영상·카드뉴스 제작 스튜디오를 보고서 관찰보다 넓게 약속할 수 있다.
- **권고:** 기능 목록에 Threads 이미지/사진/생성·Instagram 다중 슬라이드/생성·예약/정지/지연을 후속 단계로 명시한다. 초기 Instagram 단일 이미지 우선은 유지한다. 같은 자산 목록과 권리 검토를 공유하되 채널별 미디어 구성/순서/미리보기는 구별한다. 원본의 실패 재게시/고착 재전송을 그대로 복제하지 않고 unknown 대사 계약으로 보완한다.
- **수락 조건:** 단일/다중 이미지·사진 검색·AI 생성·슬라이드·즉시/예약·수동 점검 각각의 범위/미검증을 볼 수 있는 매핑이 있다. 미지원 영상/스튜디오를 사용 가능으로 표시하지 않는다. 예약/게시 연결 후에도 지연·재인증·중지 재개가 자동 재게시를 일으키지 않고 published 증거와 issues를 유지한다.

이 세 갭의 권고 경로명은 후속 제안이다. 이번 QA에서 신규 앱 메뉴/원본 소스 이식·정책/비용/지원 기능을 확정하거나 구현하지 않았다. 원본의 BYOK/평문 비밀·자체 회원관리·자동 삭제 등을 그대로 사용자 메뉴에 추가할 필요는 없으며 사이트의 승인 admin·서버 비밀 격리·증거 보존 계약과 매핑해야 한다.
