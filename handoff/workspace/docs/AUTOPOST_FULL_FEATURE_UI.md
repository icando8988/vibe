# AUTOPOST-FULL-FEATURE-UI-002 — 세 원본 프로그램 통합 기능 UI 계약

2026-11-16 · AG-UI-01 / Codex Design(배정 작업자) · Master CX-MASTER-01. Task `task_bc2514a4d80d` / dispatch `ctx_ca0e923a7728`. 상태 **ready_review / 설계 명세**. 본 문서의 메뉴·경로·필드·기능 단계는 후속 구현 계약이며 현재 서비스 지원 선언이 아니다.

## 1. 목표·기준과 단계 해석

사용자 목표는 제공된 세 원본 프로그램을 한 사이트에 병합하고 수정하는 것이다. 기존 콘솔의 콘텐츠·승인·작업·증거 경계를 유지하면서 원본의 글감 수집·생성·서식·이미지·슬라이드·예약 작업을 전체 IA에 포함한다. IGAP-01~03은 ‘제외’로 닫지 않고 아래 기능 ID와 화면 계약으로 추적한다. 실제 소스 이식·앱·SQL 구현은 Claude 담당이다.

읽은 근거는 `docs/AUTOPOST_SERVER_BRIDGE_PLAN.md` §10 전체와 관련 §3~4/§7~8, `docs/AUTOPOST_CONSOLE_DESIGN_QA.md`, 기존 UI 계획/HTML, 원본 분석 결과의 기능 목록이다. Blog 분석 §3.1~3.5, Threads 분석 §3~4, Instagram 분석 §1.1/§2.3~4.2를 부분 열람했다. 원본 코드·자산·프롬프트·키/env는 이번 작업에서 열거나 수정하지 않았다. DQ 이관 위치는 현행 globals.css 및 공통 states/작업 상세·대사 파일의 선택자/심벌 검색으로 재확인했다. 실제 기능·계정·미디어·비용·모델·성과를 실행 검증하지 않았다.

| 용어 | 의미 | 지원 여부와의 관계 |
|---|---|---|
| 현재 S0 | 보호된 콘솔의 준비 전 화면 골격, 비활성 폼·안내·미연결 상태 | 실제 저장/수집/생성/예약/외부 게시 가능 상태가 아님 |

| 후속 S2 | Threads 텍스트→단일 이미지→Instagram 단일 이미지, 브리지 I2/I3/I4 | 채널·기능별 gate를 별도로 통과해야 함 |
| 후속 S3 | Blog 서식·분류 확장, Threads 다중 이미지, Instagram 다중 슬라이드, 예약/정지. 브리지 I5를 UI 작업으로 세분화 | 원본 경로가 있어도 현재 이식/지원 완료가 아님 |

| 미검증 | 실제 서버/계정/매체/API·접근성·사용 흐름 확인이 남음 | 위 단계와 독립 축. ‘후속 예정’ 또는 문서 관찰만으로 지원 확인으로 바꾸지 않음 |

S1~S4는 날짜/인력 약속이 아닌 개발 순서다. S4 수집/후보 IA·저장 계약 설계는 S2와 병행 준비 가능하지만 외부 수집/생성은 별도 게이트를 따른다. 특정 공급자·모델 ID·가격·사용량·성공률·일정을 새로 만들지 않는다.

### 서버 브리지 10절과의 정합화

- §10.3의 AI·수집·tiptap·카드뉴스·cron-job.org ‘제외’는 **최소 이식 단계의 제외**로 읽고, 제품 전체에서 기능을 삭제하는 기준으로 사용하지 않는다. 본 문서는 수집/생성·서식·다중 슬라이드를 S3/S4로 명시하여 IGAP을 해소하는 후속 설계다. 기존 브리지 문서는 이번에 수정하지 않는다.
- 브리지의 채널별 서버 추출/대체 수정과 M1/M2/050000 원문·승인·작업 계약은 유지한다. 새 후보/생성/서식/태그/슬라이드/확장 인계 필드는 기존 테이블에 이미 있다고 가정하지 않는다.
- 원본의 회원별 BYOK·독립 회원/구독·외부 운영사 분기는 통합 목적이 아니다. 하나의 승인 admin 진입·공통 자산·서버 설정 상태로 바꾼다. 비밀값 입력 예시/로그/공개 노출을 만들지 않는다.
- Threads 단일 이미지/Instagram JPEG·다중 슬라이드·예약 한도는 실제 검증 후 규칙을 확정한다. 원본 코드의 숫자/모델 이름을 현재 서비스 제한/가용 모델로 그대로 표시하지 않는다.

## 3. 통합 메뉴와 경로 계약

공개 navigation은 유지한다. 승인 admin이 회원 영역→관리→콘텐츠 배포로 들어온다. 서로 다른 앱의 로그인·대시보드 세 개를 만들지 않고 기존 원문과 채널 리비전을 중심으로 다음 메뉴를 확장한다. 아래 신규 경로는 제안이다.

```text
    Threads·Instagram [S2]           /connections/[channel]
    생성/수집 서비스 준비도 [S4]        /connections/services
  미디어·권리                        /media, /media/[assetId]
  실행 제어 [S3]                     /operations
```

S0에 신규 준비 메뉴를 실제 추가할지는 Claude 배정 범위에 따른다. 추가한다면 ‘후속 준비’가 있는 설명 페이지로만 이동하며 비활성 항목을 클릭 가능한 게시/생성 액션처럼 만들지 않는다. 사용 가능한 메뉴는 실제 구현 단계에 따라 노출하고, 개요의 ‘후속 기능 준비’에서 전체 계획을 발견할 수 있게 한다. 다른 채널용 새 원문을 중복 생성하지 않도록 후보/생성 결과는 공통 원문에 연결한다. 채널 전용 캡션/이미지 생성은 해당 원문과 기존 리비전으로 복귀한다.

데스크톱은 기존 왼쪽 5개 주 메뉴 안에서 ‘콘텐츠’ 하위 링크를 확장하고 실행 제어를 추가한다. 모바일 960px 이하는 details 메뉴에 현재 화면/단계를 명시하고 700px 이하는 채널·후보·슬라이드·비교를 한 열로 제공한다. 긴 단계명을 가로 탭에 몰지 않는다. 검색/필터/정렬·선택 대상은 상세 왕복에서 유지하되 비밀·본문·생성 지시를 URL에 담지 않는다.

## 4. 신규·확장 화면의 입력/출력/행동·상태 계약

모든 화면은 단일 main/h1, label·legend, 텍스트 상태·차단 이유, 3px focus, 44px 타깃과 현재 토큰을 계승한다. 준비 전/불러오는 중/실제 빈 결과/부분 실패/전면 실패/권한 거부/저장 충돌을 구별한다. 접근성·반응형 실측은 후속 검증이며 지금 통과를 선언하지 않는다.

### U1. 글감 수집 /sources — F01

입력: 수집 방식(가용한 방식만 선택), 공개 출처 경로, 수집 범위·옵션, 실행 전 요약. 연결형 소스는 ‘연결 준비도’로 이동하고 비밀번호/키 입력 예시는 제공하지 않는다. 실행 범위 상한은 서버 정책이 실제 정한 값만 표시한다. 실제 계정·기사 샘플·최근 결과를 창작하지 않는다.

출력: 수집 실행의 방식/출처·요청/완료 시각·항목별 결과·중복/제외 이유·안전 오류. 다음 행동은 ‘후보 검토’이며 곧바로 생성/게시하지 않는다. 수집 요청/진행/일부 수집/완료·실패/취소 요청/취소 확인을 구분한다. 기존 성공 항목은 부분 실패로 삭제하지 않는다. 응답 유실은 기존 실행 확인이며 자동 중복 수집을 확정하지 않는다. 외부 URL은 서버에서 사설주소/리다이렉트·크기/시간 제한 등 계약에 따라 검사하고 UI는 차단 이유를 사용자가 이해할 수 있게 보여 준다.

빈 상태: ‘수집 기능 준비 전’과 ‘완료한 수집에 후보 없음’과 ‘검색 조건 결과 없음’을 구별한다. 재수집은 실제 범위/중복 처리를 확인하는 독립 액션이다.

### U2. 후보 목록/상세 /candidates — F02

정보: 제목·요약·키워드·출처 링크·수집 방식/시각·원문 발췌의 관찰 범위·중복 연결·검토 상태·연결된 콘텐츠. 선택·보류·제외 사유는 후보 상태이며 게시 작업 상태가 아니다. 출처 정정/제외는 기존 연결과 감사 이력을 보존한다.

행동: ‘이 후보로 원문 준비’ 또는 ‘선택 후보로 생성 준비’. 복수 후보는 출처 묶음과 생성 목적을 명시하고 각 결과와 출처 연결을 남긴다. 이미 원문으로 전환된 후보는 기존 원문 링크를 우선 보여 중복 원문 생성을 막는다. 원문은 검토 필요로 시작한다. 잠긴 후보·삭제된 출처·권한 변화·중복 충돌은 같은 화면에서 이유/복귀를 제공한다. 수집 성공을 사실 확인 완료 배지로 표시하지 않는다.

### U3. AI 생성 준비/결과 /generation — F03/F14

입력: 후보 또는 직접 원문, 생성 대상(공통 원문/채널 문안/이미지), 대상 채널·기존 버전/리비전, 문체/편집 요구, 출처 검토, 결과 반영 방식. 가용 모델은 검증된 서버 설정에서만 표시하며 기본 모델/예상 비용을 임의로 넣지 않는다. 비용 정책 미설정이면 실행을 막고 ‘생성 비용 설정 준비 전’을 설명한다. 예산/한도는 실제 정책이 정해졌을 때만 표시한다.

확인: 어떤 입력에서 무엇을 새로 만들지, 기존 내용 보존 여부, 생성이 승인/게시가 아님을 명시한다. 생성 결과는 새 검토 필요 초안이며 기존 승인 리비전을 덮지 않는다. 결과 문안/이미지·출처 대응·경고를 검토한 뒤 ‘새 원문으로 저장’ 또는 ‘새 리비전으로 반영’을 선택한다. 반영 전에 원문이 바뀌었으면 차이를 비교하고 재검토한다.

상태: 생성 준비/접수·처리 중/일부 결과/완료/실패/결과 확인 필요/취소 요청과 확정. ‘결과 확인 필요’는 **생성 작업 축**이며 게시 JobStatus unknown과 섞지 않는다. timeout은 결과/과금이 발생했을 가능성을 안내하고 기존 생성 이력 확인을 먼저 제공한다. 자동 반복 생성·모든 결과 소실·즉시 게시를 제공하지 않는다. 실제 사용량이 없으면 숫자를 표시하지 않는다. 키·전체 공급자 응답·비밀 프롬프트를 이벤트에 복제하지 않는다.

### U4. Blog 편집·서식·분류 /channels/blog — F05~08

고정 정보: 공통 원문 버전·Blog 리비전·제목 출처·대상 블로그·검토/승인·연결 준비도. N3(제목 저장 구조)가 미정이면 제목과 본문을 첫 줄 규칙으로 조용히 합치지 않는다. 독립 필드 계약을 추천하며 Claude/데이터 담당이 확정 후 직렬화한다.

기본 편집: 제목/본문·링크·출처. 확장 편집: 문단/제목/강조/목록·이미지 블록, 이미지 설명/권리, 태그 목록, 대상 카테고리. 서식은 안전한 미리보기와 외부 전달 형식 비교를 제공한다. 지원되지 않는 원본 서식은 어떤 부분이 텍스트로 변환되는지 저장/인계 전에 설명한다. 원본 HTML을 정제 없이 렌더하지 않는다.

태그/카테고리는 대상마다 의미가 달라서 UI 분류와 실제 블로그 카테고리 매핑을 분리한다. 미확인 카테고리/태그는 실제 외부 입력이 확인된 것처럼 표시하지 않는다. 대상·문안·서식·미디어·링크·분류 변경은 새 리비전과 승인 유효성 재검사로 이어진다.

내보내기는 제목/본문 텍스트·서식 복사와 미디어 전달/재업로드 필요 여부를 알려 준다. 실패 시 선택 가능한 텍스트 대안. ‘복사 완료’는 짧은 status이며 상태를 게시 확인으로 바꾸지 않는다. 이미지 URL의 저장/공개 수명과 사용권은 확인 근거만 표시하고 원본의 보관/자동 삭제 기간을 그대로 가져오지 않는다.

### U5. Blog 확장 연결 /connections/blog-extension 및 인계 /handoff — F09

연결 정보: 확장 설치/버전 호환·사이트 연결·대상 블로그 일치·마지막 확인/확인 불가·발급/철회 상태. 다운로드/연결이 준비 안 됐으면 비활성 사유를 표시한다. 비밀 발급 방식은 브리지 서버 계약에 따라 관리하고 값·입력 예시·평문 이력은 문서/화면 샘플에 넣지 않는다. 재연결이 새 작업을 자동 실행하지 않는다.

인계 확인: 승인 원문/리비전·제목/본문/미디어·분류·대상·현재 열린 작업/중복과 차단 이유. 승인된 manual 작업의 인계만 제공한다. 인계 상태는 **작업 상위 상태와 별도 보조축**으로 ‘인계 대기→접수 확인→입력 진행→발행 직전 준비’ 또는 ‘중단/확인 필요’를 표시한다. 이 명칭을 새 DB 상태값으로 추가하라는 지시가 아니다. 브리지의 input-result 성공은 보조 로그이고 상위 manual_ready를 published로 바꾸지 않는다.

‘마지막 발행은 직접 확인 후 누릅니다’를 인계 전·준비 결과에 반복 가능한 정적 안내로 둔다. 로그인 필요·다른 계정·비어 있지 않은 편집기·탭 닫힘/이동·입력 불일치·연결 끊김에서는 중지 이유/관찰 단계/대상 확인을 보여 주며 무조건 재입력 CTA를 만들지 않는다. 부분 입력을 자동으로 지우거나 덮지 않는다. 인계 응답 유실은 기존 작업 확인으로 간다.

실제 게시 후에는 기존 `/manual`의 ‘외부에서 게시를 마쳤습니다’→awaiting_evidence→URL/외부 ID+대상/관찰시각·시간대/방법→서버 수락 증거 후 published로 이어진다. 게시 여부가 불확실하면 unknown 대사만 제공한다. 인계 재개/재인증으로 unknown 차단을 우회하지 않는다. 수동 중단은 사유·외부 내용이 남을 수 있음을 확인하고 abandoned 키 점유를 설명한다.

### U6. Threads 이미지 /channels/threads — F10~11

텍스트/링크 편집에 단일 이미지 선택·설명/권리·규격 확인·텍스트+이미지 미리보기를 추가한다. S3 다중 이미지는 순서·개별 실패/교체·전체 준비 요약을 확장한다. S4 사진 검색/생성 결과는 공통 미디어를 통해 선택한다. 영상 파일명을 등록하는 원본 UI 흔적을 업로드/게시 지원으로 표현하지 않는다.

승인 후 실제 확인에서 대상 계정·리비전·이미지 순서·기능 검증 근거를 보여 준다. 원격 컨테이너 생성/처리/게시 요청/확인 단계는 증거와 별도 표기한다. 처리 완료는 게시 완료가 아니며 응답 유실 시 unknown. 새 시도/대사는 원문 버전·시도 이력과 연결하고 성공 채널은 반복 게시하지 않는다.

### U7. Instagram 단일/다중 슬라이드 /channels/instagram — F12~13

S2는 캡션+단일 이미지·권리·JPEG 검증/변환·미리보기. S3에서는 단일/다중 구성을 명시적으로 선택하고 슬라이드별 원본/변환 자산·문구/설명·권리·처리 상태·순서를 보여 준다. 슬라이드 교체는 이전 승인 리비전을 덮지 않는다. 드래그 외 ‘앞으로/뒤로’ 순서 버튼과 순서 변경 status를 제공한다. 아직 자산이 없으면 빈 슬라이드 시안만 두고 이미지를 창작하지 않는다.

전체 캡션과 슬라이드별 문구를 구분한다. 캐러셀은 각 슬라이드가 준비되어야 전체 승인/게시 준비를 통과한다. 자식 일부 실패·부모 처리·최종 게시 요청·외부 증거와 구성 경고를 분리한다. 이미지 수 제한/잘림 규칙/한도는 실제 검증된 규칙에서 가져온다. cap 미검증 상태에서는 ‘플랫폼 제한 확인 필요’이며 허용 숫자를 새로 만들지 않는다.

**명칭 경계:** 다중 이미지를 게시하는 캐러셀 편집은 개발 범위다. 원본 독립판에서 제한된 ‘카드뉴스 제작 스튜디오’ 전체를 제공한다고 부르지 않는다. 이미지 내 문구/디자인 자동 제작은 F03/S4의 생성 범위가 검증된 경우만 연결한다. 영상·릴스·스토리 및 스튜디오는 기능 연구/검증 항목으로 남기고 메뉴·업로드 선택을 활성화하지 않는다.

### U8. 예약 확인·큐·정지/재개 /jobs/schedule, /operations — F15~16

채널별 선택·승인 리비전·대상 계정·모드·미디어·시각/IANA 시간대·오프셋·서버 준비 조건을 확인하고 각각 접수한다. 과거/존재하지 않거나 중복되는 현지 시각은 오류와 명시적 선택을 제공한다. 플랫폼 자체 예약과 사이트 worker 예약을 혼동하지 않는다. Blog manual은 예약 게시가 아니며 확장 ‘입력 준비 시점’을 추가할 경우에도 별도 명칭/계약 없이는 제공하지 않는다.

큐는 scheduled/실행 단계·시도/지연/보류 이유·최근 확인·다음 행동을 표시한다. 특정 지연 임계값은 정책에서 받은 값만 사용한다. 원문 변경/stale은 이전 미실행 작업을 차단하고 새 승인/안전한 정리 후 새 작업. 응답 유실·정체는 게시 여부 확인을 우선한다. 취소 요청/확정·게시 요청과의 경합을 구별한다.

정지는 범위(전체/해당 채널)·사유·영향 예약·이미 발송된 요청을 막지 못할 수 있음·남는 외부 게시물을 확인한다. 실제 확인된 건수만 표시한다. 결과 안내는 ‘새 실행 중지’이며 ‘모든 게시 취소’가 아니다. 재개 후 기한 지난 예약은 새 시각/지금 실행 확인/취소를 개별 검토하고 자동 일괄 발행하지 않는다. 재인증 복구도 동일하다. unknown에는 재게시·새 작업 복제 CTA를 주지 않으며 부재 확인 뒤 별도 운영자 승인·최신 조건 재검사만 허용한다.

## 5. 전체 흐름과 인계 수락 기준

```text
수집원 → 수집 실행/이력 → 후보 검토 ─┬→ 직접 원문 준비
                                 └→ 생성 준비/결과 검토 → 새 원문 또는 리비전
공통 원문·버전 → 원문 승인 → 채널 초안(문안·서식·분류·미디어)
  → 권리/사실/링크·검증 → 채널 리비전 승인 → 선택 채널 준비 비교
    Blog → manual 작업 → 복사 또는 확장 인계 → 사람 최종 발행 → 증거
    Threads/Instagram → 준비된 기능만 즉시 요청/예약 → 단계/증거·경고
    불확실 결과 → 대사 → 게시 확인 / 부재 확인 / 여전히 불명
```

수집·후보·생성·인계·미디어 처리·승인·연결·작업 결과는 서로 다른 상태축이다. 단계가 늘어도 모든 상태를 JobStatus에 넣지 않는다. 후속 DTO에 근거·시각·계정 범위·hold/phase/issues·generation/collection/extension 실행 참조가 필요하다. 새 엔티티/열은 Claude가 기존 계약과 대조해 별도 설계한다.

원문과 채널 승인에는 브리지의 반려/철회·이력 화면을 추가한다. 철회는 이유·영향받는 미실행 작업을 확인하고 이미 외부에 게시된 내용을 지웠다고 표현하지 않는다. 생성/편집 결과 저장 중 원문 변경·승인 변경·권한 변경은 안전한 충돌 화면으로 처리한다. **입력 손실 정책:** 브리지 §4는 재조회 후 재입력을 초기 권고하지만 기존 UI 설계는 입력 보존을 권고한다. 사용자 본문을 URL/로그/임의 브라우저 영속 저장에 넣지 않는 범위에서 폼의 로컬 입력과 변경 비교를 유지하는 방안을 우선 추천하며 Claude가 서버 액션 구조와 함께 확정한다. 이 차이를 숨기고 저장 실패 시 입력을 조용히 버리지 않는다.

각 단계의 개발 완료 증거는 (a) 화면/행동 계약 구현, (b) 허용된 검증 환경에서 서버/권한/저장·중복/경합 확인, (c) 실제 기능 범위 readiness, (d) 브라우저/키보드/스크린리더·반응형 검증이다. 현재는 이 문서의 설계만 완료다. 기존 type/lint/build 통과는 이 신규 기능들의 구현/운영 성공 증거가 아니다.

## 8. 미정 정책·검증 한계

구현 전에 확정할 사항: N3 Blog 제목 직렬화, 서식/태그·카테고리/슬라이드 승인 해시 범위, 원문/채널 승인·반려/철회 동선, 후보/생성 이력·중복/보존, 수집원별 연결·권리 범위, 실제 모델/비용 정책·사용량 기록, 이미지 공개 수명/정리, 스케줄러·지연/재개, 확장 인계 복구/연결·계정 일치. 이는 전체 기능을 삭제할 이유가 아니라 단계별 활성화의 선행 계약이다. 기존 D1 승인 admin·D2 대사 후 별도 재실행 승인 원칙은 재질문하지 않는다.

브리지 §10에 기재된 소스 배치·출처/배포 조건은 Claude/Master의 이식 인계에 남긴다. 이번 작업은 그 조건을 실행하거나 저장소 공개 상태·계정/플랜을 새로 확인하지 않았다. 이미 전달된 원본 기반 이식 방향에 대해 같은 허락을 다시 묻지 않았다.

실행한 작업은 로컬 문서/소스 선택자 읽기와 허용 문서 두 개 작성뿐이다. 앱·SQL·키/env·원본 수정, commit, 외부 실행·브라우저·네트워크·DB·모델/API 호출·테스트/빌드는 하지 않았다. 기능별 현재 관찰·1차·후속·미검증과 설계 권고를 구분했으며 작업 완료는 이 명세 제출을 뜻한다. 실제 UI·이식·접근성·저장/연결/게시 정상은 후속 검증 대상이다.
