## 비교 기준

세 안은 색만 바꾸지 않았다. 시작 대상, 주 메뉴, 편집 화면의 구획/밀도, 원문 재사용을 보여 주는 위치, 모바일의 다음 화면을 다르게 설계했다. 공통 기능은 글감/후보·생성·콘텐츠/채널 편집·미디어/권리·예약/작업·Blog 확장·연결/설정이다. 각 페이지에 통합 개요·대표 편집 화면·모바일 구조와 해당 기능 위치가 있다.

예시 콘텐츠는 모두 **UI 예시·미저장**으로 표시했다. 여행·출판 실적이나 진행 캠페인·예약 일정·연결 계정·게시 성공을 만들지 않았다. C의 요일별 카드는 계획 배치 예시이며 실제 날짜/예약이 아니다. 모든 행위 버튼은 비활성이고 링크는 시안/문서 내 이동만 한다. 현재 토큰 관리 구현과 별개로 이 디자인 문서는 실제 계정/서버에 연결되지 않는다.

| 기준 | A 콘텐츠 중심 | B 채널 작업실 중심 | C 캠페인·캘린더 중심 |
|---|---|---|---|
| 첫 질문 | 무엇을 전할까? | 어느 채널을 다듬을까? | 어떤 주제/순서로 전할까? |
| 통합 개요 | 원문 보관함·작업 흐름·채널 연결 | 채널 선택 바·즉시 작업실 | 캠페인 묶음·주간 계획 |
| 실제 탐색 구조 | 왼쪽 원문 중심 메뉴→원문→채널 | 왼쪽 도구+채널 작업실→작업 문안 | 상단 캠페인/캘린더/콘텐츠 메뉴 |
| 대표 편집 | 공통 원문과 검토/채널 목록 2열, 하단 채널 초안 | 작업 목록 / 채널 편집 / 검토 inspector 3구획 | 캠페인 안 원문·채널 편집 / 채널별 준비·작업 순서 |
| 밀도 | 낮음~중간. 여유 있는 원문 집중 | 높음. 운영 정보 동시 확인 | 개요는 중간, 상세를 별도 구획 |
| 공통 원문 재사용 | 원문이 모든 채널의 중심 | 각 작업실에 공통 원문 참조 유지 | 캠페인 콘텐츠가 원문을 참조, 채널별 별도 승인 |
| 모바일 | 보관함→원문→채널, 1열 | 채널→문안 선택→편집→검토, 1열 | 주간 달력→세로 아젠다→콘텐츠 상세 |
| 장점 | 시작점 명확, 기존 콘텐츠/승인 구조와 가까움 | 채널별 반복 편집에 집중, 조건 확인 빠름 | 여러 콘텐츠·채널의 목적/순서 조망 |
| 단점 | 채널 전환을 자주 하면 이동 증가 | 높은 밀도, 공통 원문 변경 영향이 가려질 위험 | 처음 시작할 때 캠페인/시간 개념이 부담, 추가 도메인 필요 |
| 적합 사용자 | 원문 작성과 사실/권리 검토를 주도하는 운영자 | 채널별 문안/미디어를 반복 조정하는 숙련 운영자 | 여러 콘텐츠를 주제·기간 단위로 계획하는 운영자 |

## 대표 시나리오

**A:** 콘텐츠 보관함에서 UI 예시 원문 선택 → 제목·본문·출처 검토 → Blog/Threads/Instagram 초안 구성 → 채널별 승인 → Blog 수동/확장 인계 또는 준비된 API 채널의 개별 실행. 원문 편집이 시작점이므로 실제 콘텐츠 작성 단계의 혼동이 적다.

**B:** Threads 작업실 선택 → 문안 목록에서 공통 원문이 연결된 초안 선택 → 텍스트/링크/이미지 편집 → 오른쪽 검토 조건 확인. Blog 작업실은 서식·분류·확장, Instagram 작업실은 캡션·슬라이드에 초점을 둔다. 채널 작업실을 오가도 원문은 복제하지 않는다.

**C:** 캠페인 UI 예시 선택 → 날짜 없는 주간 배치에서 준비 순서 확인 → 콘텐츠 상세에서 원문/채널 문안 편집 → 계정/승인/시간대가 준비된 경우에만 실제 예약을 별도로 확인. 캠페인 카드 배치가 곧 게시 접수가 되지 않는다. 모바일은 7열 달력 대신 동일 배치의 아젠다로 전환한다.

## Claude 구현 비교

이는 상대적인 구조 비교이며 개발 시간·비용 견적이 아니다. 현재 백엔드/미검증 게이트는 디자인 선택과 별개로 유지한다.

| 구현 항목 | A | B | C |
|---|---|---|---|
| 기존 IA/경로 재사용 | 가장 가까움. 원문/초안/prepare/jobs 유지 | 기존 경로 위에 작업실 진입/문안 선택 문맥 추가 | 기존 경로 외 캠페인/계획 진입과 관계 필요 |
| 주요 프론트 작업 | 보관함·원문/채널 비교 레이아웃 | 채널 선택/작업 목록/inspector와 좁은 폭 순서 | 캠페인 개요·주간/아젠다·콘텐츠 상세 연결 |
| 추가 상태 계약 | 원문/리비전 최신성·선택 채널 | 채널·선택 원문·검토 패널 간 동기화 | 캠페인 소속·순서·미배정/계획·실제 예약 구별 |
| 주요 위험 | 원문 저장/채널 승인 경계를 조용히 생략하지 않기 | 채널 이동 시 미저장 입력·공통 원문 변경 영향 보존 | 계획을 예약 저장/실행으로 오인하지 않기, 시간대/경합 |
| 백엔드 변경 필요성 | 기본 원문/승인/작업 계약을 우선 연결 | 기존 도메인 재사용 가능, 작업실 조회 조합 필요 | 캠페인/계획 관계·권한/저장 계약 추가 필요 |
| 모바일 구현 | 2열을 1열로 | 3구획을 목록→편집→검토로 | 달력을 의미가 같은 아젠다로 |

세 안 모두 서버의 D1·승인 해시/최신성·미디어 권리·중복/대사 계약을 UI 선택으로 우회하지 않는다. Blog는 사람 최종 발행·증거, Threads/Instagram은 검증된 기능만 사용한다. 연결 인증 확인과 실제 게시 가능을 분리하고 unknown에는 재게시/복제 CTA를 두지 않는다. 영상·릴스·전체 카드뉴스 제작 스튜디오는 지원하지 않는 UI로 명시한다.

## 추천과 사용자 결정

**기준선은 A를 추천한다.** 현재 프로젝트의 공통 원문→채널 초안→승인→Blog 수동 준비 구조와 가장 가까워 정보구조 변경을 줄이면서 세 원본의 기능을 한 사이트로 모을 수 있다. 다만 이는 구현 변경량/사용 흐름에 대한 설계 판단이며 사용성 실험 결과가 아니다.

B는 채널별 반복 운영이 핵심일 때 대안이고, C는 여러 콘텐츠의 주제·일정 운영을 제품 중심으로 삼을 때 적합하다. A에서 B의 검토 패널, C의 아젠다를 후속으로 도입할 여지는 있지만 사용자 선택 전에 혼합안이나 최종 방향을 확정하지 않는다.

사용자가 확인할 기준은 ‘원문을 먼저 볼지 / 채널을 먼저 볼지 / 캠페인·순서를 먼저 볼지’다. 결정 전 web 앱에 이 디자인을 적용하지 않는다.

## 로컬 검토와 한계

Orca 내장 브라우저에서 로컬 file URL만 사용했다. 데스크톱 1440px와 모바일 폭 390px의 개요/편집 화면을 캡처했고, 960/700/320px의 문서 폭도 확인했다. 4개 HTML에서 main/h1 각 1개, 점검 폭에서 문서 전체 가로 넘침 없음, 활성 행위 버튼 없음. 내부 앵커/label·ARIA 참조의 누락은 정적으로 보완/대조했다.

스크린샷은 `evidence/`의 OPTIONS/A/B/C로 시작하는 PNG다. 모바일은 좁은 데스크톱 viewport 검토이며 실제 터치 OS/스크린리더·200% 확대·고대비/대비·전체 키보드 순회 검증은 하지 않았다. 실제 저장·계정·모델·API·게시·예약·캠페인 기능 검증은 없다. 원본 자산·외부 리소스/스크립트·키/env·실DB·네트워크를 사용하지 않았다.
