## 0. 총괄 검토 결론과 적용 원칙

**판정: 기획 기반은 충분하지만 거래 개발 착수는 조건부다.** 기존 v0.9의 기술 방향과 5개 기능 묶음은 유지한다. 사업 범위·입금 순서·목표 미달 처리·제작 및 배송 조건을 확정한 뒤 해당 거래 기능을 구현한다. 공개 콘텐츠와 공통 화면 명세는 그 전에도 준비할 수 있다.

검토일 2026-11-16 · 총괄 CX-MASTER-01 · 작업 PLAN-004 · 버전 1.0 총괄 검토안. 이 버전은 계획 산출물이며 사업 정책 승인본은 아니다.

검토 입력: 기존 통합 계획 1~19절, 지정 원본 XLSX의 전체 5시트 추출본 259줄, UI 독립 검토 UI-01~08. Claude 터미널에서 제시한 계획 요약과 파일명을 확인했다. 해당 파일의 작성 메타데이터는 CX-MASTER-01이므로 ‘Claude가 새로 작성한 별도 계획’으로 출처를 바꾸지 않았다. Claude의 기술 독립 검토 PLAN-002 결과는 현재 폴더에서 발견되지 않았다. 별도 Claude 원문이 추가되면 차이 검토 대상으로 등록한다.

**읽는 순서:** 0절에서 검토 판정과 보강 내용을 확인하고, 1~18절에서 전체 제품·설계·개발 계획을 읽은 뒤, 19절 이후의 실행 계약과 출시 기준을 적용한다. 기존 절과 보강 절이 다르면 이 문서의 보강 계약을 우선 적용하되 사용자 결정 대기는 유지한다.

## 19. 거래와 데이터의 확정 계약

아래는 Master의 기술 추천이다. 금액·환불·목표 기준 등 사업 선택은 DEC-002/003 승인 뒤 고정한다. 원문을 임의 변경해 승인된 요구로 취급하지 않는다.

### 19.1 입금과 목표 기준은 함께 선택

| 안 | 실행 순서 | 목표/미달 처리 | 영향 |
|---|---|---|---|
| A 추천·원문 순서 변경 제안 | 신청→즉시 입금 안내→운영자 입금 확인→목표 알림→제작 | 입금 확인 수량 기준. 미달 마감 시 환불 또는 연장 중 사전 고지된 정책 실행 | 미달 후 환불 운영과 선입금 안내 필요 |
| B 원문 시나리오 우선 | 신청→신청 수량 목표 달성→입금 요청→입금 확인→제작 | 유효 신청 수량 목표, 입금기한과 미입금 부족분 처리 별도 | 목표 달성 뒤 실제 입금 부족 가능, 제작 확정 조건 추가 |

두 안을 혼합해 ‘입금 수량으로 목표를 계산하면서 목표 전 입금 방법은 숨기는’ 흐름은 허용하지 않는다. 결정 전 모의 데이터로만 화면을 검토한다. 목표 알림을 받은 뒤 취소로 목표 아래로 떨어지면 현재 집계를 다시 표시하고, 제작 확정 여부와 추가 안내는 정책에 따른다. 1차 추천은 최초 달성 알림 1회이며 재달성마다 자동 재발송하지 않는다. 마감 결과는 특정 시점의 스냅샷과 집계 기준을 보존한다.

### 19.2 네 상태축과 전이 권한

기존 11절의 단일 참여 상태 나열은 설명용 요약으로 대체한다. DB에서는 다음 상태축을 분리하며, 사용자 화면은 이를 조합해 하나의 명확한 진행 문구로 보여준다.

| 상태축 | 상태 제안 | 허용 주체·핵심 제약 |
|---|---|---|
| 주문/예약 | active, cancellation_requested, cancelled, expired, completed | 본인 취소 요청, 서버 만료, 관리자 처리. 결제 여부에 따라 즉시 취소와 환불 요청 분기 |
| 입금 | unpaid, reported, verified, mismatch | reported는 회원의 확인 요청일 뿐이다. verified는 관리자가 증빙 확인 뒤 설정 |
| 이행 | not_ready, preparing, ready, shipped, delivered | 전자책은 released 상태를 별도 적용. verified 및 제작 조건 충족 전 출고·권한 부여 불가 |
| 환불 | none, requested, processing, completed, rejected | 실지급 확인 뒤 completed. 환불 누계는 확인 입금액을 초과할 수 없음 |

유효 재고 점유는 별도 예약 레코드 또는 재고 원장으로 표현한다. 재고 예약 생성/해제는 주문과 같은 트랜잭션에서 실행한다. cancelled/expired는 이미 점유 해제됐는지 기록해 중복 복원을 막는다. 배송 완료 후 반품은 새 재고 검수 사건으로 처리하며 기존 예약을 또 복원하지 않는다. 전액 환불 시 전자책 권한 회수 정책을 적용하되 이미 받은 파일을 삭제할 수 있다고 약속하지 않는다.

### 19.3 동시성·API·금액 계약

| 작업/API 제안 | 입력·응답 | 서버 보장/실패 |
|---|---|---|
| POST /api/participations | campaign_id, quantity, idempotency_key, 정책 버전 → participation_id, 서버 금액, 현재 상태 | 서버 회원·가격·시간·재고 재확인. 사용자+작업+키 유일. 동일키/다른 입력은 CONFLICT |
| POST /api/participations/:id/cancel | 이유, 요청키 → 주문/환불 상태 | 소유권 확인, 주문 잠금, 허용 전이만 실행. 입금 확인 건은 환불 절차 진입 |
| POST /api/admin/payments/:id/verify | 확인 금액, 대사 참조, 기대 버전 → 확인 결과 | 관리자 재검증. 중복 확인 집계 없음. 취소/만료 주문에 늦은 입금은 예외 대사로 이동 |
| POST /api/admin/refunds/:id/complete | 지급 확인 참조, 금액, 기대 버전 | 동일 환불 중복 완료 거절, 입금액 대비 누적 한도 검증 |
| GET /api/me/participations/:id | 본인 인증 → 최소 필요 정보 | 타인/비공개 응답과 개인 데이터 캐시 격리 |
| GET /api/me/books/:id/download | 본인·입금·배포 상태 → 만료 링크 | 비공개 저장소, 타인 권한/환불 회수/배포 전 차단 |

잠금 순서는 캠페인→주문→입금/환불→재고로 통일하고 실제 구현에서 경합 시험한다. 신청·만료·취소·입금 확인은 같은 도메인 함수를 통과하며 DB 함수 권한도 제한한다. 권한이 높은 DB 함수는 호출자 검증과 고정된 참조 경로를 가져야 한다. API 바깥의 직접 DB 호출로 검증을 우회할 수 없는지 RLS와 함수 실행 권한을 함께 검증한다.

예약 만료 시간·개인별 수량 상한은 캠페인 정책 필드로 저장하고 사전 표시한다. 만료 배치가 늦어져도 새 신청과 입금 확인의 서버 판단은 유효시간을 따른다. 마감 이후 입금 가능 여부와 입금기한은 모집 종료 시각과 별도 필드다. 늦은 입금은 자동 복원하지 않고 환불/추가 배정 중 운영자가 정책에 따라 처리한다.

종이책은 상품가+배송비-승인 할인으로 총액을 서버 계산하고 각 항목을 주문 시점에 고정한다. 1차에는 쿠폰·혼합 장바구니 없이 ‘캠페인 하나/책 형식 하나’로 제한하는 안을 추천한다. 전자책은 주소를 받지 않는다. 10% 수수료는 적용 대상·기준액·반환 시 차감·반올림 단위가 확정되기 전 자동 계산/정산하지 않는다. 부분·과입금은 mismatch로 두고 자동 입금 완료 처리하지 않는다.

## 20. 화면 상태·접근성·콘텐츠 인수 계약

| 화면/서버 상태 | 표시 문구 | 가능한 행동과 복구 |

| S07 pending | 회원 승인 대기 중 | 승인 상태 다시 확인·문의. 원래 책/수량 복귀 정보 유지 |
| S07 rejected/suspended | 가입 승인되지 않음/이용 제한 | 공개 가능한 사유·문의 경로. 비활성 버튼만 남기지 않음 |
| S08 submitting | 신청 내용을 확인하고 있습니다 | 반복 제출 억제. 응답유실 시 같은 요청키 재조회·재시도 |
| S08 SOLD_OUT/NOT_OPEN | 남은 수량이 바뀌었습니다/신청 기간이 아닙니다 | 입력 보존, 상세 최신 수량·일정으로 돌아가기 |

| S09 refund processing | 환불 처리 중 | 요청 금액·접수 상태·문의. 완료 전 ‘환불됨’ 표시 금지 |
| S09 ebook not_ready/expired link | 출간 준비 중/다운로드 링크가 만료됨 | 준비 일정 또는 본인 권한 재확인 뒤 링크 재발급 |

로그인/승인 뒤 돌아오면 보존한 상품·수량만 복구하고 가격·재고·시간·정책을 다시 조회한다. 회원 승인과 상품 반려의 내부 메모는 공개 사유와 분리한다. 전자책/종이책 폼과 완료 메시지를 구분하고 주소 변경은 출고 전까지만 허용하는 안을 제안한다.

필수 접근성 인수안: 본문 18px 권고, 조작 영역 44px 권고, 200% 확대, 320 CSS px 재배치, 키보드 전 과정, 초점 표시, 폼 라벨·입력 오류 연결·제출 결과 알림, 수량 직접 입력과 증감 조작, 동작 감소 설정 대응. 일반 텍스트 대비 4.5:1을 제안 합격값으로 사용하고 구현 시 공식 기준과 실제 측정으로 확정한다. 이 문서 작성으로 접근성 적합 판정을 내리지 않는다. 16절의 ‘선택 접근성 강화’는 추가 편의 기능만 뜻하며 이 필수 인수 항목은 제외할 수 없다.

연락 경로와 거래 관련 FAQ 내용은 필수다. 별도 문의함·독립 FAQ 페이지·공개 새소식 목록은 선택이다. 공지 등록 기능은 원문 필수이며 중요한 제작/배송 변경 내용을 기존 상세·마이페이지에서 확인할 수 있어야 한다. S01 실제 사진은 승인 자료 확보 시 사용하며, 없으면 동의된 텍스트 소개로 대체한다.

## 22. 총괄 실행 일정과 인수 지점

착수일 D0는 사용자가 계획과 해당 단계의 사업 범위를 확인한 날이다. 아래 5주는 초기 가정이며 3~5주 추정의 상세 전개다. 기존 공수 합계는 약 17~27 작업일로, 병행 가능 범위와 외부 대기에 따라 달력 기간이 늘 수 있다. 12/25는 연도·공개 범위를 확정하기 전 확약하지 않는다.

개발 담당은 계획상 역할이다. 실제 작업 배정에는 세션 수락과 수정 범위를 기록한다. 기존 TEAM의 busy 표시를 현재 활동 증거로 간주하지 않는다. 현재 검토에서는 새 작업자를 실행하거나 다른 세션에 입력하지 않았다. Master가 직접 작업할 때도 고유 ID를 쓰고 migration·공통 설정·lockfile은 한 번에 한 담당만 수정한다.

### 베타 과제와 성과 측정

읽기 전용 베타는 목적·책 조건·참여 경로를 1분 내 찾고 설명하는 과제를 수행한다. 모의 거래 베타는 승인된 테스트 계정으로 신청→내역→입금 확인 요청의 차이를 확인하고 취소까지 수행한다. 외부 채널은 외부 이동 인지와 외부 내역 확인 경로를 평가한다. 실송금이나 실기부를 베타 과제로 요구하지 않는다.

제안 합격 기준은 지인 10명 중 8명 이상 도움 없이 해당 베타 유형의 종료점 도달이다. 핵심 고령 사용자와 모바일/PC 이용자를 포함하도록 모집하되 실제 표본·도움 여부·실패 단계·소요시간을 기록한다. 승인 대기를 실패와 혼동하지 않는다. 300회원/30구매 목표는 정식 공개 후 1개월 기준이며 모의 계정·취소 주문·외부 이동은 제외한다.

## 23. 운영 인수·장애 대응·출시 중지 기준

| 운영 항목 | 책임/주기 제안 | 감지·처리·인수 증거 |
|---|---|---|
| 입금/환불 대사 | 운영자 매일, 실제 가능한 시간 확정 | 주문 기대액·실입금·환불액 대조, mismatch/늦은 입금 예외함, 조정 이력 |
| 알림/예약 만료 | 시스템 실행기+운영자 매일 확인 | 실행 마지막 성공 시각, 실패 수, 지연 예약, 제한 재시도 후 수동 재처리 |
| 주문·재고 불일치 | Master/개발 운영 담당 | 재고 음수·중복 예약·환불 초과는 즉시 신청 중지, 원장과 실제 상태 대사 |
| 제작/배송/전자책 | 운영자, 변경 발생 시 | 제작 지연 공지, 출고 기록, 링크 만료 재발급, 반송 문의 경로 |
| 백업/복구 | Master, 공개 전 및 중요 변경 전 | 격리 환경 복원 시험, 복구 시점과 소요시간 실측, migration 호환성 확인 |
| 비용/권한 | 계정 소유자+Master, 주간 검토 | DB/저장소/이메일 사용량, 경보 임계치, 유료 전환 결정 근거 |

복구 목표 제안은 데이터 손실 허용 24시간 이내, 주요 거래 복구 1작업일 이내다. 계정 플랜과 실제 백업 제공 기능을 확인하고 복원 시험으로 검증하기 전 운영 보장으로 표시하지 않는다. 앱 롤백만으로 DB 변경이 복원된다고 가정하지 않으며 이전 앱과 호환되는 migration을 우선한다.

즉시 공개 중지 조건: 타인 개인정보 접근, 관리자 자기 승격, 초과 재고, 중복 입금 확정/환불, 전자책 무권한 공개, 비밀값 노출, 주문 소실, 실제 판매 조건 부재. 중지 시 신규 신청을 잠그고 기존 내역·문의 경로는 유지한다. 원인·영향 주문·부분 처리 여부를 확인한 뒤 복구/재처리한다. 배치·알림을 무조건 재실행하지 않는다.

출시 인수 묶음: 확정 요구 목록, 실행한 시험/미실행 시험, 실제 콘텐츠·정책, 운영자 매뉴얼, 테스트 데이터 제거/격리, 백업·복구 근거, Git SHA/배포 ID/DB 버전, 알려진 제한, 담당 연락 경로. 결함이 없는 척하거나 화면 완료를 운영 완료로 보고하지 않는다.
