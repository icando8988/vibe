# 세계일주·출판·참여 플랫폼 통합 개발 플랜

작성: 2026-11-16 (Asia/Seoul) · 버전 0.9 검토안 · 책임 CX-MASTER-01 · 작업 PLAN-001

이 문서는 지정 기획서의 분석 결과와 개발 가능한 보완 설계다. 원문 요구, Master 추천, 사용자 확정 필요 사항을 구분한다. 실제 앱 구현·결제·배포는 수행하지 않았다. 원문이 요구하는 기획 확인 후 개발 순서를 유지한다.

## 1. 사업 방향과 권고안

**권고 방향:** 원민철의 자전거 세계일주 도전을 이야기와 검증 가능한 기록으로 소개하고, 그 이야기를 담은 책의 구매 참여 및 외부 펀딩으로 연결하는 사이트를 만든다. 출시 초기에는 일반 다품종 공동구매 플랫폼보다 프로젝트 자체의 신뢰와 출판 참여에 집중한다.

한 줄 소개 제안: “원민철의 자전거 세계일주 도전과 출판 여정을 기록하고, 책과 응원으로 함께하는 공식 프로젝트 공간.” 문구는 초안이며 공식 브랜드/기록 인증을 주장하지 않는다.

현재 기획은 개인 도전·출판과 다수 판매자가 상품을 올리는 공동구매 플랫폼의 요구가 함께 들어 있다. 따라서 **A안: 운영자 중심 출판 프로젝트**와 **B안: 승인된 일반 판매자 공동구매 플랫폼**을 구분한다. 추천은 A안이다. B안에 해당하는 셀러 등록·상품 승인 기능은 원문 요구를 삭제하지 않고 별도 선택 범위로 보존한다. 사용자 답변 전에도 두 안에서 공통인 화면·DB 명세·공통 흐름 설계는 진행 가능하다.

사이트의 직접 고객 문제는 원문에서 ‘해당없음’이다. 보완 가설은 ① 어떤 도전이고 믿을 수 있는지 한 곳에서 알고 싶다 ② 책 구매/후원 방법과 진행 상태를 쉽게 확인하고 싶다 ③ 참여 뒤 입금·제작·배송 상태를 알고 싶다 이다. 지인 10명 테스트에서 실제 문제인지 확인한다.

## 2. 입력 자료와 분석 한계

기준 파일: `(원민철)드림AI_바이브코딩_비즈니스_사이트_기획서_디자인_v2_개발용.xlsx`.
다른 `(1).xlsx` 복사본은 분석 기준에 혼합하지 않았다. 원본은 수정하지 않았다.

| 시트 | 확인 범위 | 분석 결과 |
|---|---|---|
| 1_비즈니스 플랜 | 저장된 셀과 수식 전체; 핵심 E17:E59, 결과물 B64:E71 | 사업·디자인·연동 방향 있음. 예시 열 D와 입력 열 E가 광범위하게 동일하며 예시 혼입 여부 판단 필요 |

| 3_화면 목록 | 전체 셀; C11:G24 | 실제 화면 행 14개 모두 미작성. 10행은 예시 |

| 5_AI 전달용 | 전체 셀·수식·저장된 계산값 | 첫 시트 내용을 참조함. 기능/화면/데이터 전달 칸은 원시 시트 공백으로 비어 있음 |

분석은 OOXML에서 셀 주소·문자열·수식·저장값을 직접 추출했다. 수식을 Excel에서 재계산하거나 화면 렌더링을 시각 검수하지 않았다. 패키지 항목 목록에 이미지·차트·주석 부품은 발견되지 않았다. 색·병합·글꼴을 독립 디자인 시안으로 평가하지 않았다. 추출 근거는 `../planning-source-extracted.txt`, 재현 코드는 `../extract-planning.ps1`이다.

첫 시트 E8의 ‘30/30, 100%’는 사업 질문 채움 표시다. 기능 상세·화면·데이터 설계와 개발 준비 완료를 뜻하지 않는다. 결과물 E64:E71도 모두 ‘미착수’다. C8 한 줄 소개는 비어 있어 AI 전달용 C12가 ‘미작성’이다.

외부 참고 사이트·기네스 규정·법률·서비스 요금의 현재 상태를 조사한 문서가 아니다. 문서 속 기록·기부·판매 표현은 검증된 사실로 전환하지 않는다. 기술 버전과 상품 요금은 구현 착수 시 공식 자료와 실제 계정으로 확인하며 현재 확정하지 않는다.

## 5. 제품 목표·성과 측정

1차 가치 흐름: 도전 이해 → 책/캠페인 탐색 → 참여/외부 펀딩 → 내 진행 확인 → 제작/발송 안내.
원문 목표: 공개 1개월 내 회원 300명, 구매 30건. 추천 정의: 테스트/중복 계정을 제외한 이메일 확인 및 승인 회원, 입금 검증된 취소되지 않은 주문 수. 외부 펀딩 클릭은 구매가 아니다. 외부 구매는 신뢰할 수 있는 제공 자료를 확보한 경우만 별도 집계한다.

계측 이벤트: project_view, campaign_view, participation_started/completed/cancelled, external_funding_click, payment_verified, fulfillment_completed. 이벤트에 이메일·주소·은행정보 원문을 넣지 않는다. 유입 경로와 단계별 전환/이탈을 집계한다. 목표 달성 수치·실제 참여와 임의 데모 숫자를 섞지 않는다.

검증 가설: 지인 10명 중 8명 이상이 1분 안에 프로젝트 목적·책 참여 방법을 설명할 수 있고, 8명 이상이 도움 없이 핵심 신청을 완료한다. 이는 제안한 베타 합격 기준이며 이미 달성한 수치가 아니다.

## 6. 개발 범위와 우선순위

1차 필수는 다음 5개 묶음으로 관리한다. 로그인·권한·정책·오류 처리는 각 묶음의 필수 기반이다.

| ID | 기능 묶음 | 포함 기능 | 완료 조건 |
|---|---|---|---|
| F01 | 프로젝트/출판 탐색 | 홈·소개·책/캠페인 목록/상세·필터/검색·계획/공지 | 승인된 공개 자료만 노출; 검색 0건·미출간·외부 링크 오류 상태 처리 |
| F02 | 인증과 권한 | 이메일/카카오 로그인, 가입 동의, 승인 상태, 역할 | 비회원 로그인 복귀, pending 차단, 일반회원 관리자 URL/API 접근 거절 |
| F03 | 참여·취소·수량 | 수량·가격 스냅샷, 중복방지, 마감, 최소 목표/최대 재고, 내역 | 동일 요청 반복 1건, 경계시각과 동시 신청에서 초과 재고 없음 |
| F04 | 마이페이지/수동 입금 운영 | 참여/취소 내역·입금 안내·관리 확인·제작/배송 상태 | 본인 내역만 열람; 입금 확인은 관리자만; 취소/환불 분리 |
| F05 | 운영 관리와 알림 | 회원/상품 승인, 공지, 참여 XLSX, 목표/마감 이메일 | 미승인 노출 불가; 민감정보 제한; 목표·마감 논리 이벤트 중복 방지·실패 재처리 |

R06의 회원 상품 등록은 B안 선택 시 F05에 seller 전용 신청→검토→승인 흐름으로 포함한다. A안 선택 시 운영자가 콘텐츠를 등록한다. 이 차이는 사용자 결정 전 구현으로 고정하지 않는다.

1차 보완 필수: 서버 검증·권한 격리·감사 기록·백업/복구 절차·문의 경로·정책 버전 동의·개인정보 최소화·접근성·SEO 메타·실제 데이터 기반 운영 지표. 이는 기존 목표의 안정적 운영을 위한 제안이다.

1차 선택: 여정 계획 페이지, 새소식, FAQ, 공유 링크/OG 이미지, 관리자 문의함. 책 정보·참여 핵심 흐름보다 늦게 만든다. 문의함을 생략하면 공개 운영 연락처가 있어야 한다.

1차 제외 유지: 사이트 카드결제, 실시간 채팅, 네이티브 앱, 리뷰, 다국어. 예약·일반 커뮤니티·AI 추천/챗봇·실시간 위치 추적·SNS 자동 게시도 이번 필수 범위에 추가하지 않는다. 지원하지 않는 기능의 작동 버튼을 만들지 않는다.

## 7. 사용자와 핵심 흐름

| 역할 | 공개 조회 | 신청/취소 | 등록 | 관리 |
|---|---|---|---|---|
| 방문자 | 공개 콘텐츠만 | 로그인으로 이동 | 불가 | 불가 |
| pending 회원 | 공개+자신의 승인 상태 | 승인 전 불가(원문 기준) | 불가 | 불가 |
| 승인 회원 | 공개+본인 내역 | 가능; 정책/기한 적용 | A안 불가 | 불가 |
| 승인 seller(B안) | 본인 상품/집계 | 본인 참여 가능 여부 정책 정의 | 본인 초안/검토요청 | 타인의 개인정보 불가 |
| 관리자 | 업무에 필요한 범위 | 입금/취소·환불 운영 | 승인·반려·게시 | 회원·콘텐츠·내보내기 |

직접 신청: 홈 → 상세에서 책 종류·가격·목표·마감·판매주체 확인 → 로그인/동의 → 승인 상태 확인 → 수량 입력 → 서버 재검증 → 신청 완료/입금 안내 → 관리자 입금 확인 → 마이페이지 상태 확인 → 출판/발송.

외부 펀딩: 홈/상세 → 외부 서비스로 이동한다는 안내 → 검증된 캠페인 링크 → 외부 서비스에서 신청/결제. 돌아왔다는 이유로 성공 처리하지 않는다. 동기화가 없으면 외부에서 확인하도록 안내한다.

취소: 내역 → 취소 가능 조건 조회 → 사유/확인 → 서버 상태 전이와 재고 복원 → 결과. 입금 완료 주문은 단순 삭제가 아니라 취소 요청→환불 처리→완료로 관리한다.

관리: 로그인 → 역할 확인 → 회원/캠페인 검토 → 게시 → 참여/입금 확인 → 목표 및 마감 점검 → 제작/배송 → 집계. 일반 회원 화면을 숨기는 것으로 보안을 대신하지 않는다.

## 9. UI·UX·콘텐츠 설계

원문 색상: primary #2563EB, accent #F97316, background 흰색. 주황색을 작은 흰색 글자의 배경으로 무조건 쓰지 않고 실제 대비를 확인한다. 기본 본문 제안 18px, 줄높이 1.6, 조작 영역 최소 44px, 키보드 탐색·눈에 보이는 포커스·폼 라벨·스크린리더 오류 연결을 확인한다. 이는 고령층을 포함한 타깃을 고려한 제안값이다.

## 11. 상태 모델과 핵심 불변식

캠페인 검토 상태: draft→pending_review→approved/rejected. 모집 상태: scheduled→open→closed 또는 cancelled. **최소 목표 달성은 모집 상태와 별개 속성/이벤트**다. 목표를 넘었다고 재고가 소진된 것은 아니다. 게시/검토/모집/재고 상태를 한 열에 혼합하지 않는다.

참여: awaiting_payment→payment_reported→payment_verified→fulfillment_pending→fulfilled. awaiting_payment는 정책 기한 안에서 cancelled/expired 가능. payment_verified 이후는 cancellation_requested→refund_pending→refunded로 추적하며 처리 전 환불 완료를 표시하지 않는다. 반려·실패 사유와 전이 주체를 기록한다. 채널 external은 내부 입금/배송 상태를 자동 생성하지 않는다.

원자적 처리: 신청 트랜잭션에서 승인·공개·모집시간·수량·최대수량을 검증하고 재고 예약과 참여를 함께 저장한다. 취소/만료도 상태 전이와 재고 복원을 같은 트랜잭션으로 처리한다. 클라이언트 표시 수량은 정보이며 최종 판정은 서버다. 브라우저 재시도/더블클릭은 idempotency_key로 같은 결과를 반환한다.

지표는 ① 신청 수량 ② 유효 예약 수량 ③ 입금 확인 수량 ④ 출고 수량을 구분한다. ‘남은 수량’은 max_qty에서 유효 예약을 뺀 값이고 ‘목표까지’는 min_goal_qty와 비교한다. 무제한 모집은 남은 재고를 꾸며 표시하지 않는다. 목표 달성 알림이 신청 기준인지 입금 기준인지는 DEC-003에서 확정한다. 기본 추천은 입금 확인 수량 기준이다.

마감은 서버 시간으로 `now < closes_at`일 때만 신청 허용한다. 배치가 늦어도 API는 마감을 집행한다. 외부 이메일은 DB 트랜잭션 안에서 직접 보내지 않고 outbox에 저장한다. 전송 성공 후 상태 기록 실패 시 재전송 가능성을 고려하며 제공자가 지원하면 멱등키를 사용한다. 정확히 한 번 발송을 근거 없이 보장하지 않는다.

## 12. 권한·보안·개인정보

공개 조회는 published/approved 콘텐츠만 허용한다. 참여·주소·입금·전자책 권한은 본인과 적법한 업무 권한의 관리자만 접근한다. B안 seller에게는 본인 상품과 필요한 집계만 제공하며 배송 개인정보의 접근 범위는 별도 정책으로 정한다.

DB RLS를 테이블별로 설계하고 anonymous/member-A/member-B/seller/admin의 실제 쿼리로 검증한다. 클라이언트 입력의 user_id·price·role·payment_status를 신뢰하지 않는다. 서비스 권한 키는 서버에만 두며 모든 관리자 쓰기는 서버에서 역할을 다시 확인한다. 저장소 파일 경로를 알아도 비공개 전자책/주소가 공개되지 않도록 한다.

관리자 계정 생성/역할 부여는 운영자 확인 절차로 제한한다. 인증 리디렉션 목적지 제한, 업로드 유형·크기 검증, HTML 정제, 제출 빈도 제한, 다운로드 접근 만료를 포함한다. 로그에 비밀번호·토큰·전체 주소·전화번호를 남기지 않는다.

전자책은 기술적으로 무단 복제를 완전히 막는다고 약속하지 않는다. 본인 다운로드 권한과 짧은 링크, 배포 기록을 우선한다. 개인정보 보유기간·환불/배송 정책·기부 관련 표현은 운영주체와 실제 절차를 확정하고 적절한 검토를 거쳐 공개한다. 이 문서는 법적 적합성 판정이 아니다.

## 13. 구현 구조와 외부 연동 계획

기술 스택은 원문 Next.js + Supabase + Vercel을 유지한다. 구현 착수 시 실제 프로젝트/계정 소유권·지원 버전·런타임·요금/한도를 확인해 고정한다. 현재 루트에는 앱 소스가 없어 build/test 명령을 확인하지 못했다. 원문 ‘계정 ✔’는 현재 연결 성공 증거가 아니다.

논리 구조: 공개/회원/관리 UI → 서버 경계(인증·입력·권한) → 도메인 서비스(참여/입금/상태 전이) → Supabase DB/Auth/Storage. 알림은 outbox→실제 실행기→이메일 제공자→결과 기록. 작은 서비스로 시작하고 별도 마이크로서비스는 만들지 않는다.

모듈 계약: 콘텐츠 공개조회, 인증/승인, 캠페인 조회·관리, 참여 생성·취소·조회, 입금 확인·환불 기록, 출고/전자책 권한, 알림, 감사/집계. 도메인 오류는 UNAUTHENTICATED/FORBIDDEN/NOT_OPEN/SOLD_OUT/INVALID_QUANTITY/CONFLICT 등으로 구분하고 사용자가 다음 행동을 알 수 있게 표시한다.

카카오: 개발자 앱·리디렉션·동의 항목·운영 URL을 실제 콘솔에서 확인해야 한다. 미연결은 버튼 숨김/준비 중 처리; 이메일 경로로 공통 흐름을 검증할 수 있다. 이메일: 제공자·발신 도메인·샌드박스/운영 자격을 확인하고 테스트 수신자만 발송한다. 블로그/인스타 자동 게시, 텀블벅 비공식 스크래핑은 구현하지 않는다.

환경: local/dev→비공개 preview→production. 데이터/자격정보를 분리하고 예시 env에는 값 대신 이름만 기록한다. cron/스케줄러 사용 전 실제 제공 기능과 간격·한도를 확인한다. 유료 서비스 도입은 필요 시 가격/대안/영향을 담은 결정을 받는다. 기존 API KEY.txt/DB 비밀번호 파일은 이 분석에서 읽지 않았다.

배포 시 Git SHA·migration 버전·배포 ID·검증 시간을 연결한다. 공개 전 backup/restore와 롤백을 검증한다. destructive migration은 자동 승인 대상으로 삼지 않는다. 이번 문서 작성은 배포 승인을 요청하거나 실제 공개하는 작업이 아니다.

## 18. 협업 운영과 현재 확인 수준

Master가 작업 분해→단일 담당 배정→범위 협조→결과 회수→통합→검증→보고를 운영한다. 일반 기술 승인과 역할 배정은 위임 범위 안에서 수행하며 외부 권한 자체를 새로 부여할 수는 없다.

계획상 역할: CX-MASTER-01 운영/통합, CC-ENG-01 설계·로직·DB, AG-UI-01 Codex Sub UI·미디어·자료. AG 명칭은 사용자 지정 역할 ID이며 Antigravity 실행 성공을 뜻하지 않는다. 실제 등록·수락은 .ai/TEAM.md와 dispatch 증거로 관리한다.

지금 확인된 것: Codex CLI 0.169.0, Claude Code 2.1.325 설치; Orca에서 현재 Codex/기존 Claude/추가 Codex 터미널 조회 가능. Antigravity 계열 명령과 dev-requests는 PATH에서 찾지 못했다. 여러 장비 동기화·클라우드 계정·운영 배포는 확인하지 않았다.

충돌 방지: 공식 작업 상태는 Master 단일 기록, 작업자 결과는 고유 파일. UI/도메인/DB 계약을 먼저 합의하고 migration/lockfile/공통 설정은 순차 수정한다. 현재 Git 저장소가 아니므로 branch/worktree 격리를 이미 제공한다고 말하지 않는다. 앱 착수 시 자료 폴더와 자격정보를 함께 저장소에 올리지 않도록 격리한다.

문서만으로 백그라운드 자동운영이 생기지 않는다. 실제 Orca worker 수락/반환은 별도 기록하고, 미연결 상태는 prepared로 유지한다. 초기 운영 기록은 `.ai/`를 참조한다.
