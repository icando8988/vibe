# AUTOPOST-BLOG-CONNECTION-UX-005 — Blog 확장 연결·인계 UX 정적 검토

2026-11-17 · AG-UI-01 / Codex Design(배정 작업자) · Master CX-MASTER-01. Task `task_326b8e0ea9e5` / dispatch `ctx_9e21967e3df5`. 상태 **ready_review**. 앱·서버·확장 수정 없이 정적 소스만 검토했다.

## 1. 판단과 읽은 범위

발급 전 준비 상태·승인 admin 판정·토큰 목록·발급·철회·최소 연결 인증 응답의 코드 경계는 존재한다. 그러나 이를 실세션·DB 적용·확장 연결 성공으로 판단하지 않았다. 실제 발급 화면의 값은 보지 않았고 실제 토큰·키/env·DB·로그를 읽거나 출력하지 않았다. 이번 문서는 코드의 필드/심벌·분기·문구를 근거로 한다.

필수 입력 전체: `web/src/app/admin/distribution/connections/blog-extension/{page.tsx,token-issue-form.tsx,actions.ts}`, `connections/page.tsx`, `web/src/server/distribution/blog/{token-service.ts,whoami.ts}`, `web/extension/naver-blog/SETUP.md`. 보충으로 `components/distribution-console/console-shell.tsx`, `server/distribution/blog/extension-auth.ts`, `server/distribution/write-runner.ts`를 읽어 공통 안내와 불확실 응답/인증 결과를 대조했다. 원본 프로그램·확장 실행 코드·SQL·키/env는 열지 않았다.

현재 사실과 판단:

- 페이지는 준비 전/목록 성공/목록 오류를 분기하고, 목록을 확인할 수 있을 때만 발급 폼을 표시한다. D1 서버 판정과 액션의 actor 재검사가 선언되어 있다.
- 서버 발급 결과는 일회 응답 경로로 값이 전달되고 목록은 메타데이터만 파싱한다. 목록에 예상 밖 열이 섞이면 거부한다. 이는 정적 관찰이며 저장/네트워크의 실제 비밀 비노출을 검증한 결과가 아니다.
- 발급 폼은 label·유효기간·pending 버튼, 결과와 복사, 오류 alert를 제공한다. 닫기·명시적 값 노출 종료, 복사 실패 안내와 복사 상태 초기화가 없다.
- whoami 핸들러의 성공은 최소 연결 인증 확인만 의미한다. 네이버 로그인·대상 블로그 일치·작업 인계/입력 준비가 확인됐다는 정보는 없다.
- 새 handoff API는 Claude 구현 중이다. 이번에는 구현 상태를 확인하지 않았고 아래 §4를 **후속 UX 계약 제안**으로만 기록했다. SETUP의 ‘다음 작업’ 표기가 현재 개발 완료 여부를 증명하지 않는다.

기존 DQ-01~08의 CSS/모바일·전체 메뉴·기술 의존성 계층·상태 사전·타깃 크기는 `docs/AUTOPOST_CONSOLE_DESIGN_QA.md`, `docs/AUTOPOST_FULL_FEATURE_UI.md` §6을 참조한다. 동일 결함을 새 건수로 재등록하지 않았다. 아래 항목은 새 Blog 연결 수명주기에서 확인한 구체적 문제다.

## 2. Claude 수정 항목

### BC-01 · 일회 표시 종료 동작과 결과 수명주기 부재 — P1, 실제 발급 사용 전

- **파일/위치:** `token-issue-form.tsx:21~24,46~74` 및 `actions.ts:16~28`.
- **사실:** 발급 성공 뒤 값·복사 UI는 결과 상태가 유지되는 동안 남고 ‘닫기/값 표시 종료’ 동작이 없다. 폼도 계속 보여 다시 발급할 수 있으며 pending 동안 이전 결과를 별도로 종료하지 않는다. ‘화면을 벗어나면 다시 볼 수 없음’ 안내만 있다.
- **사용자 영향:** 복사·확장 입력을 마친 뒤 민감한 표시만 닫을 수 없어 페이지를 떠나야 한다. 새 발급으로 이전 표시가 교체될 때 어느 발급 건인지 혼동할 수 있다. 이를 실제 유출이 발생했다는 증거로 해석하지 않는다.
- **Claude 수정안:** 발급 성공 화면을 별도 표시 세션으로 관리하고 ‘값 표시 종료’를 제공한다. 종료는 DOM 노출과 클라이언트 상태의 참조를 끝내되 토큰 철회와 구별한다. 종료 전 재조회 불가·미복사 시 복구 절차를 안내하고, 같은 표시 세션에서 무심코 추가 발급하지 않도록 ‘다른 토큰 발급’을 별도 진입으로 둔다. 단순 CSS 숨김만으로 종료하지 않는다. ‘닫기’가 클립보드나 확장에 이미 저장된 값을 지운다고 약속하지 않는다.
- **수락 조건:** 키보드로 발급 결과→복사/수동 선택→표시 종료에 도달한다. 종료 후 값이 DOM/표시 상태에 남지 않고 메타데이터·목록으로 복귀한다. 종료가 철회·연결 성공·인계 실행으로 처리되지 않는다. React 상태 처리상 가능한 참조 해제 범위만 보장하고 메모리 완전 소거를 주장하지 않는다.

### BC-02 · 복사 실패가 침묵하고 새 결과에도 이전 복사 상태가 남을 수 있음 — P2

- **파일/위치:** `token-issue-form.tsx:23,61~70`.
- **사실:** 복사 실패 콜백은 copied=false만 설정한다. Clipboard API가 없는 경우도 사용자 안내가 없다. copied는 발급 결과가 바뀔 때 초기화하지 않으므로 앞선 결과에서 true가 된 뒤 새 결과가 나타나면 ‘복사했습니다’가 그대로 남을 수 있다.
- **사용자 영향:** 복사 안 된 값을 복사했다고 믿거나 실패 이유를 모른 채 발급을 반복할 수 있다. 현재 코드 분기에서 가능한 문제이며 브라우저로 재현한 것은 아니다.
- **Claude 수정안:** 복사 상태를 idle/pending/succeeded/failed로 구분하고 발급 결과/표시 세션이 바뀌면 초기화한다. 미지원/권한 거부/실패에는 ‘복사하지 못했습니다. 표시된 값을 직접 선택해 복사하세요’를 제공한다. 수동 선택 가능한 읽기 전용 영역과 label을 제공하되 자동으로 전체 값을 낭독하지 않는다.
- **수락 조건:** 첫 발급 복사 성공 후 다음 발급은 미복사 상태다. 복사 거절/미지원에서 오류와 수동 대안이 보이고 발급 요청을 다시 보내지 않는다. 성공 status는 현재 표시 세션의 실제 복사 성공 뒤에만 나타난다.

### BC-03 · 불확실 발급 응답을 ‘발급 실패’로 단정하는 제목 — P1, 실제 발급 사용 전

- **파일/위치:** `token-issue-form.tsx:12~18,76~80`, `token-service.ts:143~161`, `write-runner.ts:46~54`.
- **사실:** unavailable 안내 본문은 목록 확인을 요구하지만 결과 상단은 항상 ‘발급하지 못했습니다’다. bad_response도 failed로 매핑되고 일반 실패 문구는 잠시 뒤 재시도를 권한다. RPC 이후 응답이 없거나 파싱이 안 됐다는 사실만으로 DB에서 발급되지 않았다고 확정할 수는 없다.
- **사용자 영향:** 발급된 값은 회수하지 못했는데 실패로 오인해 새 발급을 반복할 수 있다. 원문을 다시 조회할 수 없는 구조라 목록에서 발급 결과를 먼저 확인해야 한다.
- **Claude 수정안:** 확정 입력/권한/준비 전 거부와 ‘발급 결과 확인 필요’를 구분한다. 불확실 응답은 상단부터 ‘발급 여부를 확인해야 합니다’로 표시하고, 명시적인 목록 재조회/결과 비교 동선을 둔다. 원문 재표시 대신 새 메타데이터 확인→필요한 대상 철회→새 발급 순서를 안내한다. 같은 이름이 있을 수 있으므로 이름 하나만으로 새 발급 대상을 단정하지 않는다. 서버가 가진 안전한 요청 식별/시각·목록 비교 정보를 활용할 계약은 Claude가 정한다.
- **수락 조건:** RPC 응답 유실·잘못된 성공 응답에서 ‘미발급 확정’이나 자동 재발급 없음. 재조회가 실패하면 불확실 상태를 유지한다. 단순 새로고침으로 잃은 값을 복구할 수 있다고 안내하지 않는다. 식별 안 된 토큰을 임의 철회하지 않는다.

### BC-04 · 철회가 즉시 제출되고 처리 중·영향 확인이 없다 — P2

- **파일/위치:** `blog-extension/page.tsx:90~106`, `actions.ts:31~37`, `page.tsx:19~27`.
- **사실:** 목록의 철회는 확인 단계 없이 바로 서버 액션으로 제출된다. 대상 label은 접근 가능한 버튼 이름에 포함되어 있지만 pending·영향/마지막 확인·취소 동선은 없다. 철회 성공 문구는 연결 중단을 설명하지만 외부 입력/게시가 남는 경계는 설명하지 않는다.
- **사용자 영향:** 사용 중인 연결을 실수로 중단할 수 있고 응답을 기다리며 반복 클릭할 수 있다. 이미 확장에 전달된 내용이나 진행 중인 요청까지 취소됐다고 오인할 여지가 있다.
- **Claude 수정안:** 대상 이름·유효/만료·최근 사용 정보와 ‘이 연결을 쓰던 확장의 다음 인증이 거부됨’을 확인한 뒤 철회한다. 진행 중 입력·외부 게시의 취소/삭제를 보장하지 않는 문구와 취소 동선을 제공한다. 처리 중 재제출을 막고 결과/불확실 응답은 목록 재조회로 확인한다.
- **수락 조건:** 키보드로 대상→확인→안전한 취소 또는 철회→같은 목록 결과에 도달한다. 만료와 철회를 구분하고 이미 철회된 대상은 재철회 행위가 없다. 철회가 사람 게시/증거 기록을 취소했다고 표시하지 않는다.

### BC-05 · 만료 시각의 시간대가 결과와 목록에서 다르다 — P2

- **파일/위치:** `blog-extension/page.tsx:30~31,94~99`; `token-issue-form.tsx:49~50`.
- **사실:** 목록 fmt는 Asia/Seoul을 명시하지만 발급 결과는 브라우저 기본 시간대를 사용한다. 화면에는 기준 시간대 표시도 없다. 유효기간 선택은 코드에서 정해진 값이며 이번 검토가 새 기간을 정한 것은 아니다.
- **사용자 영향:** 다른 시간대의 관리자에게 같은 만료 시각이 다른 숫자로 보여, 잘못된 발급 건이나 만료 연장으로 오해될 수 있다.
- **Claude 수정안:** 발급 결과·목록·철회 확인의 표시 시간대를 통일하고 명시한다. null 최근 사용은 ‘사용 기록 없음/미확인’ 등 조회 계약에 맞는 의미로 풀어 쓰고 만료/철회 후 다음 행동을 안내한다.
- **수락 조건:** 같은 발급 건은 브라우저 시간대와 무관하게 동일 기준으로 표시되거나 일관된 사용자 시간대 정책을 따른다. 기준 시간대가 눈에 보이고 만료가 실제 외부 게시 상태를 바꾸지 않는다.

### BC-06 · 토큰 유효·인증·인계 준비도가 같은 ‘연결’로 보인다 — P2

- **파일/위치:** `connections/page.tsx:21~35`; `blog-extension/page.tsx:30,48~50,127~132`; `whoami.ts:20~24`; 공통 `console-shell.tsx:93~95`.
- **사실:** 부모 화면은 Blog를 ‘연결 대상 아님’이라 하면서 확장 토큰 관리 링크를 제공한다. active 토큰은 최근 사용이 없어도 ‘사용 중’으로 표시된다. whoami 성공은 인증 확인만 반환하는데 발급 페이지 소개는 확장 입력 동작을 현재형으로 설명한다. 공통 shell은 모든 저장/연결/표시 상태가 실제 결과 아님을 일괄 안내하므로 서버 준비 후 실제 토큰 결과가 나타나는 분기와 충돌할 수 있다.
- **사용자 영향:** 토큰 발급/유효를 확장 연결·네이버 계정 확인·인계 준비 완료로 오인하거나 실제 발급 결과를 샘플로 오인할 수 있다.
- **Claude 수정안:** ‘Blog 수동 게시’와 ‘확장 인증 연결’을 분리한다. active는 ‘유효’로 표시하고 실제 사용 기록을 별도로 둔다. 준비도는 ①토큰 발급 가능 ②확장 서버 인증 확인 ③대상 블로그/설치 버전 확인 ④인계/보고 API 준비 ⑤입력 작업 실행·증거로 나눈다. 현재 존재하는 근거만 채운다. shell은 실제 지원된 토큰 관리와 미구현/미검증 게시 기능을 분리해 안내하되 live gate는 유지한다.
- **수락 조건:** 유효하지만 미사용인 토큰이 연결 성공으로 표시되지 않는다. whoami 성공만으로 대상 블로그 일치/작업 API 사용 가능을 확정하지 않는다. 서버 준비 전에도 계획된 인계 기능을 실행 완료처럼 표현하지 않는다. 일반 사용자에게 새 운영 데이터 노출은 없다.

### BC-07 · 일회 값이 live status 안에 있고 오류가 필드/결과 포커스로 이어지지 않는다 — P2

- **파일/위치:** `token-issue-form.tsx:27~43,47~55,76~80`; `actions.ts:16~26`.
- **사실:** 발급 결과의 role=status 컨테이너가 민감한 값의 표시 영역까지 포함한다. 오류는 alert지만 invalid를 한 문장으로만 표시하고 필드별 오류·aria-invalid·오류 요약 이동은 없다. 결과 제목으로 포커스를 옮기는 선언도 없다. 실제 낭독이나 브라우저 포커스 이동은 이번에 측정하지 않았다.
- **사용자 영향:** 보조기기에서 전체 값이 원치 않게 낭독될 가능성이 있고 이름/기간 중 무엇을 고칠지 파악하기 어렵다.
- **Claude 수정안:** live status는 ‘발급 결과 준비됨’ 같은 짧은 비밀 없는 문장으로 한정한다. 값 영역은 label 있는 읽기 전용/선택 가능 구획으로 분리하고 사용자 요청 시 접근하게 한다. 새 결과의 제목·메타데이터와 안전한 행동을 먼저 찾도록 초점을 관리한다. 서버 필드 오류를 안전한 코드로 반환해 해당 필드 aria-invalid·도움말에 연결한다. 철회/발급 오류에 로그인/목록 복귀도 제공한다.
- **수락 조건:** 화면 진입/결과 알림이 전체 값을 자동 낭독하지 않도록 구조가 분리된다. 키보드로 값을 선택/복사/닫기할 수 있고 invalid가 정확한 필드로 연결된다. 실제 스크린리더 낭독은 후속 검증 전 통과로 쓰지 않는다.

### BC-08 · 설치 안내·whoami 계약이 구현과 불일치하며 사용자 동선은 저장소 경로에 멈춘다 — P2

- **파일/위치:** `web/extension/naver-blog/SETUP.md:20~41`; `whoami.ts:20~24`; `blog-extension/page.tsx:127~137`.
- **사실:** SETUP은 서버 API를 전부 미구현으로 묶고 whoami의 응답을 사용자/권한 표시 필드 중심으로 기술한다. 실제 읽은 핸들러는 최소 인증 성공·준비 전·인증 불가만 응답한다. UI는 설치 안내로 저장소 파일 경로만 적어 일반 탐색 링크/설정 화면 동선이 없다. 확장 클라이언트가 현재 응답을 소비하는지는 이번 범위에서 읽거나 실행하지 않았다.
- **사용자 영향:** 어느 단계까지 연결 가능한지 판단하기 어렵고 개발 파일 수정과 사용자 설치/연결 작업을 혼동할 수 있다. 응답 차이가 실제 확장 오류를 일으켰다고 확정하지는 않는다.
- **Claude 수정안:** SETUP/클라이언트/핸들러 계약을 정합화하면서 인증 확인과 작업 API 준비를 기능별로 구분한다. 관리자 화면에는 준비된 설치 안내·안전한 다운로드/설정 경로만 제공하고 개발용 파일 편집은 진단 문서로 분리한다. 미배포이면 ‘설치/연결 준비 전’과 복귀 링크를 표시한다.
- **수락 조건:** 인증 확인 응답의 실제 의미와 설치 문서가 일치하고 불필요한 사용자/권한 식별 정보로 응답을 확대하지 않는다. 준비되지 않은 API를 작동한다고 표현하지 않는다. 연결 화면→설치/설정 안내→연결 화면의 복귀 경로가 명확하다. 새 handoff 구현 완료 여부는 Claude의 최신 결과와 대조한 뒤 문구를 갱신한다.

## 3. 발급 전부터 종료·만료까지 권고 화면 흐름

| 상황 | 기본 표시/행동 | 성공으로 오인하지 않을 조건 |
|---|---|---|
| 서버 준비 전 | 토큰 관리 준비 전, 발급 비활성·일반 사용자용 사유, 목록/연결 화면 복귀 | 키·DB 실제 설정을 확인했다고 표시하지 않음 |
| 목록 실패 | 조회 실패+명시적 재조회, 발급은 보류 | 목록 0건/미발급으로 바꾸지 않음 |
| 발급 가능·빈 목록 | 이름/기간 label, 기간 정책 설명, 일회 표시 안내와 다음 연결 단계 | 확장/인계 준비도는 별도 |
| 발급 중 | 버튼 중복 제출 잠금, 발급 중 안내, 이전 표시 세션 종료/보존 정책 명시 | 이전 복사 성공 문구 재사용 금지 |
| 발급 성공·값 표시 | 이름/만료·시간대/메타데이터→명시적 값 접근/복사·수동 선택→값 표시 종료 | 발급 성공≠서버 인증 확인≠네이버 대상 확인 |
| 값 표시 종료 | 안전한 메타데이터/목록과 복귀, 재조회 불가·손실 시 철회/재발급 안내 | 종료≠철회. 클립보드/확장 저장 내용을 지웠다고 하지 않음 |
| 결과 불명 | 발급 여부 확인 필요, 목록 재조회·식별/철회 검토 | 자동 재발급·미발급 확정 없음 |
| 유효/미사용 | ‘유효’와 최근 사용 기록을 분리 | ‘사용 중/연결됨’ 자동 부여 없음 |
| 만료/철회 | 원인·시각/기준 시간대·재연결 경로, 재발급 전 대상 검토 | 원래 게시 작업 결과나 외부 게시물을 바꾸지 않음 |
| 인증 불가 | 확장에는 일반적인 인증 불가와 관리자 목록 확인 동선 | unauthenticated에게 만료/철회/권한상실 세부를 분리 노출할 필요 없음 |
| 인증 확인 | 서버 인증 확인+확인 시각(실제 응답 근거가 있을 때) | 작업/입력결과 API와 대상 계정 준비도는 별도 |

whoami의 401은 없음·철회·만료·권한 상실을 의도적으로 구별하지 않는다. UX 개선을 위해 공개 인증 응답에 민감한 원인/계정 정보를 추가할 필요는 없다. 권한 있는 관리자는 자신의 토큰 목록에서 확인 가능한 메타데이터만 보고 복구한다. 503은 ‘서버 준비 전/일시 확인 불가’로 안내하며 임의로 만료라고 단정하지 않는다.

## 4. 후속 handoff 상태 계약 제안 — 현재 구현 보장 아님

새 인계 API는 Claude 구현 중이므로 다음 표는 UI와 서버 DTO가 맞춰야 할 **목표 계약**이다. 새 SQL enum/엔드포인트/실제 실행 기록이 존재한다고 가정하지 않는다. 상위 manual 작업 결과와 확장 인계 보조 단계·연결 인증·콘텐츠 승인 상태를 분리한다.

| 단계 | 화면에 필요한 사실/정보 | 허용되는 다음 행동·서버 확인 조건 |
|---|---|---|
| H0 인계 준비 | 승인된 Blog 원문/리비전·대상 블로그·manual 작업·미디어/분류·연결 및 작업 API readiness | 최신 승인/권리·중복·대상·D1/확장 인증을 서버가 검사한 뒤 인계 요청. 준비 전에는 비활성+사유 |
| H1 접수 확인 | 서버가 확인한 작업·실행 참조, 접수 시각, 고정 리비전 | 확장 수신/작업 가져오기 기다림. 접수 응답 유실은 기존 작업 확인, 같은 내용 재인계 금지 |
| H2 입력 중 | 같은 실행 참조의 claim·최근 heartbeat·마지막 관찰 단계·대상 일치 | 진행 조회. heartbeat 정체를 실패/재전송 허가로 바꾸지 않음. 중단 요청/확정 구별 |
| H3 입력 결과 확인 | 준비 완료/중단/일부 입력/확인 필요와 근거·버전/대상 일치 | 준비 완료라도 상위 published 아님. 계정 불일치/기존 편집/탭 이동·닫힘/내용 불일치는 그대로 중지·검토; 덮어쓰기/자동 재입력 없음 |
| H4 사람 발행 확인 | 최종 발행은 사람이 직접 누른다는 안내, 승인본/대상·인계 결과 | 실제 외부 게시를 마친 운영자의 명시적 선언만 기록. 준비 완료를 자동 게시 선언으로 바꾸지 않음 |
| H5 증거 대기 | 상위 awaiting_evidence, URL 또는 외부 ID·대상·관찰 시각/시간대·확인 방법 | 서버 수락 증거 뒤만 게시 확인됨. URL 자동 크롤링/입력만으로 검증 완료를 암시하지 않음 |
| H6 게시 확인 | 수락된 증거와 확인자/시각·원문/리비전·대상 | 이력 조회/정정. 구성 경고·늦은 증거가 있으면 독립 표기하고 다시 게시하지 않음 |
| HU 게시 여부 불명 | unknown·관찰 근거·최근 시도/리비전·대사 필요 | 대사만. 재인계/재게시/복제·재인증 우회 없음. 부재 확인 후 별도 운영자 승인·조건 재검사 |
| HA 중단 | 사유·입력된 외부 내용 잔존 가능성·상위 manual 결과와 키 점유 | 중단 이력 확인. 중단≠외부 내용 삭제. 새 버전으로 중복 차단 우회를 권하지 않음 |

### 전이·경합에서 필요한 UX 규칙

1. 접수/입력결과/사람 게시/증거 저장은 각기 서버가 확정한 결과만 표시한다. UI optimistic 성공으로 단계나 published를 건너뛰지 않는다.
2. 토큰 만료/철회/권한 상실은 다음 인증/보고의 실패 원인일 수 있지만 이미 입력·게시된 내용은 남을 수 있다. 연결 복구→기존 작업 조회→담당자 확인 순서이며 새 요청을 자동 재전송하지 않는다.
3. 원문·초안 변경은 고정 리비전과 최신 버전 차이를 표시하고 미실행 인계를 차단한다. 입력 중 변경은 이전 실행을 조용히 최신 본문으로 갈아끼우지 않는다. 변경된 내용의 승인/새 작업 전환은 서버 정책과 함께 별도 확인한다.
4. 늦은 입력결과·다른 실행 참조·이미 만료된 lease의 보고는 ‘최근 보고/충돌 검토’로 보존할 계약이 필요하다. 늦은 응답으로 현재 입력 단계나 확정 증거를 덮지 않는다.
5. 발행 직전 준비가 지연/정체돼도 외부 게시 부재가 아니다. 인계 처리 불명과 실제 게시 unknown은 관찰 단계에 따라 구분하되 판단 근거가 없으면 재전송을 유도하지 않는다.
6. 키보드는 연결→원문/승인본→인계 확인→진행→증거/대사→복귀 순으로 이동하고, 동적 단계 업데이트가 초점을 빼앗지 않게 한다. 요약 상태만 live로 알리고 비밀/원문 전체·시간마다 반복되는 heartbeat는 낭독하지 않는다.

권고하는 작업 상세 상단: **상위 수동 작업 상태 / 인계 보조 단계 / 승인 최신성 / 연결·기능 준비도** 네 축과 다음 행동. 아래에 승인본·대상, 시도/인계 결과, 사람 게시 선언, 증거/대사 이력을 순서대로 배치한다. 기능 미준비와 진행 중 잠금의 사유를 구분한다. 기존 ‘연결·준비도’로 돌아가도 같은 작업 문맥으로 복귀할 수 있게 하되 비밀/본문은 URL에 담지 않는다.

## 5. 구현 이관과 검증 한계

Claude 우선순위: BC-01/03(실제 발급 전 수명주기·불확실 결과) → BC-02/04/05/07(복사·철회·시간대·접근성) → BC-06/08(준비도/문서·설치 동선). 인계 구현과 §4의 단계·행동 DTO를 함께 정합화한다. DQ-01~08 공통 수정은 기존 작업표를 참조하며 본 문서에서 중복 결함 수로 세지 않는다.

이번 완료는 **정적 UX 검토 8건과 인계 계약 제안 제출**이다. 앱·SQL·확장을 수정하지 않았으며 실세션 브라우저·실DB·토큰 발급/복사/철회·whoami 호출·인계·네이버 게시·스크린리더/키보드·반응형·클립보드 권한은 실행 검증하지 않았다. 이전 로컬 HTML 브라우저 허용을 실앱 검토에 사용하지 않았다. 문구/분기상 가능성과 실제 재현을 구분했으며 토큰 원문·계정·키/env를 읽거나 예시로 만들지 않았다.
